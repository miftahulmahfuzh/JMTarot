## Detailed Requirements Understanding

**Problem/Requirement Statement**

The group chat is architecturally **timeless and amnesiac**, and both properties were deliberate,
documented decisions that this workstream reverses under an explicit ruling.

- **Timeless.** `build.ts`'s `ageLabel` renders *relative ages only* and its header states the
  reason: *"THE SERVER DOES NOT KNOW THE QUERENT'S TIMEZONE … a relative age is true in every
  timezone."* `direct/window.ts`'s `[F2-16]` says the same and adds that the bucket list *"stops at
  kemarin and contains no 'pagi tadi', a phrase that would need a wall clock the server has not
  got."* The premise — the server cannot know the offset — is what R1 falsifies: the browser
  knows, the column to hold it already exists, and nothing but a client field is missing.
- **Amnesiac.** The room's memory is exactly four blocks, all of them either fixed at onboarding
  (`<penanya>`, `<jawaban>`), derived from readings (`<riwayat>`), or a rolling 40-message window
  (`<obrolan>`). **Nothing is ever distilled out of the conversation itself.** There is no table,
  no op and no prompt block for a fact the querent stated in the room.

**Success Criteria**

- **R1.** Every chat prompt — director and voice — states the querent's current local date, weekday
  and wall-clock time, resolved through a real UTC offset the browser reported. A reader referring
  to a clock time uses `nanti` / `tadi` correctly relative to that time. `chat_threads.utc_offset_minutes`
  is written and read.
- **R2.** A `user_memory`-shaped row per querent, produced by a model reading the room and updated
  as the conversation continues; it survives beyond the 40-message window, is fenced in the prompt,
  is erasable, is named in `/privacy`, and is visible to the querent on `/account`.
- **R3.** Measurably more proactive and more human: new time- and profile-anchored material kinds,
  a looser proactive policy that no longer fires at 3 a.m., and a rewritten director rule set that
  licenses longer, more interactive runs. **The gate is the blind read**, `npm run smoke -- --chat`
  and `--chat --proactive`, not a unit test.

**Key Considerations**

1. **Three standing decisions are reversed, by name, and each must be recorded rather than
   silently edited:** `build.ts`'s no-clock rule, `[F2-16]`'s bucket vocabulary, and `[R17]`'s
   Option A on quiet hours (which folded `utc_offset_minutes` in *for exactly this day*).
2. **R2 stores model-written inferences about a real person.** That is a stronger privacy claim
   than anything in the database today: `readings.question` and `chat_messages.body` are text the
   *querent* typed, and the six onboarding answers are fenced by `C-D8`'s five conditions. A
   sentence the model wrote *about* someone, stored and re-read into every future prompt, needs
   the same treatment — including the `C-D8` ban on saying **how you know**, which is what turns
   *"nasi padang lagi kan?"* (a friend) into *"you said on the 9th you like nasi padang"*
   (surveillance).
3. **`C-D6` survives the cost ruling.** Chat calls stay `deferred`; the reading still wins.
4. **The compile-guard surface is unusually wide.** A 14th `LLMOp` is a compile error in two
   `AssertNever` guards until classified, `callClass.test.ts` fails on a *dead* op (declared with
   no call site), and `flagCoverage.test.ts` asserts the set of provider call sites is **exactly**
   its two tables. So the op, the flag and the call site must land in one phase.
5. **The 40-message window is the reason R2 exists, and it must not simply be widened.** Raising
   it to 200 would put three weeks of chatter in front of the instruction and dilute it —
   `memory.ts`'s dilution argument. A distillation is the answer; a bigger window is not.

## Current Dataflow

### Entry Point A: `POST /api/chat/message` — the querent speaks

**Location:** `src/app/api/chat/message/route.ts`
**Guard:** `requireUser()` (onboarding required). **Limits:** `chat:post:<uid>` 60/hr **plus**
`refusalsExhausted(uid)`. **`maxDuration = 20`, `runtime = 'nodejs'`.**
**Headers received:** `x-jm-session`, `x-jm-local-date` (`YYYY-MM-DD`).
**Body:** `{ body, reply_to_message_id?, attached_reading_id?, client_key?, attached_from? }`.

1. `sanitizeAnswer(body, MAX_CHAT_MESSAGE_LENGTH=2000)` — rejects, never truncates.
2. Idempotency: `messageByClientKey` returns the stored row as a 200.
3. Attachment ownership is a `WHERE user_id = $caller` predicate, not a 403 branch.
4. `moderate(body, locale)` — W7's gate. A refusal is a **403 `RefusalNotice`**, never a bubble.
5. **One transaction:** `insertMessage` → `upsertThread(lastUserMessageAt)` →
   `supersedeReadingRun` (when attaching) → `mintRun({ trigger: 'user_message' })`.
6. `after()`: `chat.message_sent`, `recordModerationFlag`, `hitRefusal`.

**The local date is read here** (`:398`) for the analytics context and **is discarded**; it never
reaches the run row or any prompt.

### Entry Point B: `POST /api/chat/advance` — one beat

**Location:** `src/app/api/chat/advance/route.ts`. `maxDuration = 60`, 400/hr.
**Receives `x-jm-local-date` and ignores it entirely.** This is the route on which every chat model
call happens, and therefore the route R1 must thread a clock through.

`advance({ userId, locale })` → `run.ts:200`:

1. `owner = randomUUID()`; `claimRun(db, userId, owner, LEASE_SECONDS=90)`.
2. `nextAction(run)` (`machine.ts`, pure): `done|abandoned` → idle; `beats === null` → **plan**;
   `beatsDone >= total` → finish; else **execute** `beats.beats[beatsDone]`.
3. **plan** → `doPlan()` → `direct/plan.ts:66` → `buildPlanPrompt` → provider (`op: 'chat_plan'`,
   `callClass: 'deferred'`, `model: chatModel()`) → `validatePlan` → `planFallback`.
4. **execute** → `doBeat()` → `voices/turn.ts:72 speak()` → `buildTurnPrompt` → provider
   (`op: 'chat_turn'`) → `validateTurn`; **one retry inside the same request**.
5. `completeBeat(...)` writes 1–2 bubbles under the lease guard.

**Neither `DirectorInput` nor `VoiceInput` carries a `localDate` or an offset.** Both prompt
builders fabricate one:

```ts
// direct/prompt.ts:115  and  voices/prompt.ts:89
localDate: new Date().toISOString().slice(0, 10),
```

with a comment permitting it *only* because its single use is the floor of a 30-day lookback:
*"Anything that RENDERS a date to a person must not do this; nothing here does."* **R1 makes
something render a date to a person, so that permission expires.**

### Entry Point C: `GET /api/chat/state` — the badge poll, and the proactive tick

`maxDuration = 30`, 240/hr. Four reads, each individually swallowed. When `chatProactiveEnabled()`
it reads `x-jm-local-date` and runs `proactiveTick({ userId, locale, localDate })` in `after()`.

**Defect found, and it is on R3's critical path.** `ChatButton` — the badge poller mounted on
`/`, `/[reader]`, `/account` and `/history` — sends **only** `x-jm-session`
(`src/components/ChatButton.tsx:93`). Every proactive tick fired from those four pages therefore
runs with `parseLocalDate(null)` → the UTC fallback, i.e. **the wrong calendar day for ~7 hours
every night in Jakarta**, which is exactly the window the daily cap and the occasion detectors
are keyed on. Only a tick fired from inside `/chat` gets the querent's true day.

### The prompt assembly (the heart of R1 and R2)

`assembleChatContext(db, args)` — `src/lib/chat/context.ts:238`. Six concurrent reads under
`Promise.all`, **every one individually `.catch()`ed**; the assembler never throws.

| Read | Source | Feeds |
|---|---|---|
| `getProfile` | `profiles` | nickname, birth date → numerology |
| `getAnswers` | `onboarding_answers` (**the one decrypt**) | `<jawaban>`, voice profile only, behind `chatAnswersEnabled()` |
| `readLotusBlock` | `lotus_avatars` | `<penanya>` background line |
| `recallableReadings` | `readings` (5, 30 days) | `<riwayat>` |

`buildChatPrompt` (`prompt/build.ts:511`) returns **`{ system, user, maxTokens }` and nothing
else** — `[F3-5]`, the structural guarantee that a decrypted answer cannot reach a browser.

**The user turn is exactly five blocks, four fenced and one not:**

```
<penanya>   who they are          (background)
<jawaban>   what they said        (voice profile only)
<riwayat>   what they drew
<obrolan>   the room              (nearest the instruction)
GILIRANMU:  the one unfenced block — the instruction
```

The block order is the injection answer: *material is fenced, instruction is not*.
**There is no block for "what time it is" and no block for "what we know about them from this
room".** R1 adds the first; R2 adds the second.

`CHAT_MAX_TOKENS = 90` (`src/lib/prompt/budget.ts:366`) bounds one bubble.

### `personas` / `lotus_avatars` — `schema.ts:1057` / `:257`
The precedent for a per-user generated artifact: `user_id` PK + cascade, payload, `input_hash`,
`source_version`, `model` (+`prompt_version`), `created_at`, `updated_at` **set by hand inside
`onConflictDoUpdate`**. Staleness resolves `absent | source-version | user-edit | drift | fresh`,
`user-edit` **before** the hash arm. **No locale in the hash** — a language switch must translate,
never regenerate.

**The asymmetry R2 must choose a side of:** `lotusInputHash` is static, so a stored fallback
matches its own hash for ever → the flag writes **nothing**. `personaInputHash` ends with the last
ten reading ids, so it moves and heals → the flag stores the **template**.
