## 1. What the user asked for, and what that forces

> *"clicking this, inside user can click History, which will redirect user to all
> his history items. user can click the item, and it will open the card selection
> just like at the time they did it in the past."*

> *"History (/history): clicking this will open up a new page. in the new page,
> maybe add a filter by date button, so user can only see the list of History
> items for a day. default to today's date."*

Three things fall out of the second sentence of the first quote, and they are the
three that shape everything below.

**"Just like at the time they did it" is a reconstruction, not a re-run** (VD14).
The reading already exists in `readings.body`; regenerating it would cost a model
call and produce *different prose*, so the querent's memory of what they were told
and the app's would disagree. That is precisely the failure the memory features
exist to avoid, and it is why the detail screen has no fan, no reshuffle, no
retry, and no return-card button. `CardDetail` already takes `onReturn` as
optional and renders nothing when it is absent — VD14 is satisfied by omitting a
prop, which is the cheapest possible enforcement.

**AMENDED 2026-08-28, NARROWLY, AND THE BOUND IS THE WHOLE OF IT.** VD14's
argument is about a reading that HAS prose — *"the querent's memory of what they
were told and the app's would disagree"* — and it does not reach a row stored with
`body IS NULL`, where there is nothing remembered for a regeneration to disagree
with. `/history/[id]` therefore offers `Coba ulang` on exactly that set and on no
other: `src/lib/reading/retryable.ts` answers from `body IS NULL`, **never from a
status list**, so `partial` — which has real prose that simply stops — is never
retryable. The refill updates the row in place and never touches `reading_cards`,
so the reconstruction VD14 is really about is unchanged: same cards, same
orientations, same slots. Everything else in the paragraph above is intact — no
fan, no reshuffle, no return-card button, and `CardDetail` is still mounted
without `onReturn`.

**"The card selection" means the slot row, not the fan.** The fan is 22 face-down
cards and an act of choosing; there is nothing left to choose. What the querent
remembers seeing is three cards face up in three labelled slots, and tapping one
opened it large. `Slots` + `CardDetail` is that screen, and reusing them rather
than reimplementing them is the whole substance of "the exact same UI".

**Defaulting to today means most visits show an empty page.** Most people do not
read every day. This is the same tension `DaySummary` and `FrequencyLine` faced
under M14 and it resolves the *opposite* way here — see D6.

## 3. `ReadingView` — the shared renderer (VD10)

**This section is the interface V7 depends on. It is restated verbatim in
`## Interfaces I export` and the two must not drift.**

### 3.1 The boundary, stated deliberately

`ReadingView` is `'use client'` and it obeys four rules, each of which exists
because V7 is mounting it on a page that is outside every fence this app has.

1. **No session.** It never calls `useViewer()`, never imports `@/lib/auth/**`,
   never assumes a cookie. Everything it knows arrives as props.
2. **No fetch.** It issues no network request. The prose it renders is handed to
   it. See H2.
3. **No database types.** `src/lib/clientBoundary.test.ts` forbids *any* import
   matching `@/lib/db/` from a client component, and its regex matches
   `import type` as well — so `ReadingStatus` cannot come from `@/lib/db/schema`.
   The type moves to `src/data/types.ts` and `schema.ts` imports it from there,
   exactly as `Locale`, `ReaderId`, `ServiceId` and `YesNo` already do. Declared
   in `## Schema deltas`.
4. **Everything it renders is serialisable except `footer`.** `footer` is a
   `ReactNode`, which a server component may legally pass to a client component,
   and it is the slot V7 puts `ShareFooter` in and `/history` leaves empty.
   `onCardOpened` is optional so a server component can mount the whole thing
   with no callback at all.

### 3.2 What it renders, top to bottom

```
   service name                     -- serviceById(serviceId).name[t.locale]
   reader name  ·  26 Juli  19.40   -- viewer's locale; see 3.3
   "Pertanyaanmu: …"                -- only when `question` is non-null
   [ slot row, faces up ]           -- <Slots showFaces>, tap opens <CardDetail>
   YA / TIDAK / BELUM JELAS         -- yesno services only, from readings.verdict
   the prose                        -- original, or translated, or unavailable
   the entertainment disclaimer     -- common.disclaimer.long, as on the draw screen
   {footer}                         -- V7's ShareFooter; nothing on /history
```

No fan. No hint. No question *input*. No counter. No reset. No retry.

### 3.3 Which locale governs which string

**Chrome follows the viewer; prose follows `readings.locale` until it is
translated.** Service name, reader name, slot labels, the date, the verdict word
and the disclaimer all come from the message catalog or from `Localized<>` data
files, and they render in `t.locale` — VD8 says so directly ("what is actually
rendered in a list is metadata which the message catalog already localizes"). The
querent saw *Yang udah lewat*; an English viewer today sees *What's done*, and
that is correct, because the label is the app speaking and the app speaks the
viewer's language.

Only `readings.body` is bound to the language it was generated in, and that is
VD7: the row is immutable, the translation is a derived row, and `readings.locale`
never moves.

### 3.4 The component

`src/components/ReadingView.tsx`:

```tsx
'use client';

/**
 * ONE RENDERER, THREE MOUNTS (roadmap VD10). History detail, V7's public share
 * page, and — when someone gets to it — the post-reading screen.
 *
 * FOUR RULES, AND EACH ONE IS THERE BECAUSE OF THE PUBLIC MOUNT:
 *
 *   1. NO SESSION. No `useViewer()`, no `@/lib/auth/**`, no assumption that a
 *      cookie exists. `/s/[slug]` is in `isPublic()`, so `requireUser()` never
 *      runs above it and a component reaching for a viewer there throws for a
 *      stranger and works for everyone on the team.
 *   2. NO FETCH. The prose is handed in. The share page cannot call V2's
 *      authenticated `/api/translate`, and a component that fetched would force
 *      either an open translation endpoint or a second renderer. A second
 *      renderer is the thing VD10 exists to prevent.
 *   3. NO `@/lib/db/**` IMPORT, NOT EVEN `import type`.
 *      `src/lib/clientBoundary.test.ts` matches `from '...'` regardless of the
 *      `type` keyword. `ReadingStatus` therefore lives in `@/data/types`.
 *   4. IT NEVER RENDERS `reading.body` IN A LANGUAGE THE VIEWER IS NOT READING.
 *      See `resolveProse` below. This is the invariant, not the caller's
 *      discipline: a caller who forgets `prose` gets the translating state, not
 *      an Indonesian paragraph inside an English app.
 *
 * READ-ONLY (VD14). No fan, no picking, no reshuffle, no reset, and `CardDetail`
 * is mounted WITHOUT `onReturn`, which is what removes the return-to-deck button.
 * Reconstruct, never re-run: regenerating would cost a model call and produce
 * different prose, so the querent's memory of the reading and the app's would
 * disagree — the exact failure the memory features exist to avoid.
 */
import { useState, type ReactNode } from 'react';
import { CardDetail } from './CardDetail';
import { Slots } from './Slots';
import { cardById } from '@/data/deck';
import { readerById } from '@/data/readers';
import { serviceById, slotLabels } from '@/data/services';
import type { Draw, Locale, ReaderId, ReadingStatus, ServiceId, YesNo } from '@/data/types';
import { formatLocalDate, formatTime } from '@/lib/i18n/format';
import { useT } from '@/lib/i18n/LocaleProvider';
import styles from './ReadingView.module.css';

/** One card as `reading_cards` stores it. Ids, never resolved objects (H1). */
export type ReadingViewCard = {
  /** 0..21. */
  cardId: number;
  reversed: boolean;
  /** 0-based slot in the spread. */
  position: number;
};

/**
 * A completed reading, flattened for rendering. EVERY FIELD IS JSON-SAFE.
 *
 * `localDate` IS A STRING AND `createdAtIso` IS A STRING, for two different
 * reasons that are both worth knowing:
 *
 *   - `localDate` is the QUERENT'S calendar day (roadmap §7). A `Date` renders in
 *     the server's zone and is a day out for anyone in Jakarta between midnight
 *     and 07:00. There is an integration test that fails if anyone "fixes" the
 *     column to `mode: 'date'`, and this type is the same rule one layer up.
 *   - `createdAtIso` is a real instant and a `Date` would be correct — but this
 *     object arrives over JSON from `/api/history` on one path and out of an RSC
 *     payload on the other, and one shape for both paths is worth more than the
 *     type. Parse it at the point of formatting.
 */
export type ReadingViewData = {
  id: string;
  readerId: ReaderId;
  serviceId: ServiceId;
  /** `'YYYY-MM-DD'`. The querent's own day. */
  localDate: string;
  createdAtIso: string;
  /** The language the PROSE came out in. Immutable (VD7). NOT the viewer's. */
  locale: Locale;
  status: ReadingStatus;
  body: string | null;
  /** The machine verdict from `effectiveYesNo()` at draw time. Never re-derived. */
  verdict: YesNo | null;
  /**
   * The querent's own typed text, or null.
   *
   * V7 PASSES NULL UNLESS `share_links.include_question` IS TRUE (VD9). This
   * component renders whatever it is given and makes no policy decision about
   * it; the policy lives in the resolver that builds the object.
   */
  question: string | null;
  cards: ReadingViewCard[];
};

/**
 * What prose to show, and whether more is coming.
 *
 * A UNION AND NOT THREE BOOLEANS: "translated but also still streaming" and
 * "original but unavailable" are states that cannot be represented, which is the
 * point.
 */
export type ReadingProse =
  | { kind: 'original' }
  | { kind: 'translating'; text: string }
  | { kind: 'translated'; locale: Locale; text: string }
  | { kind: 'unavailable' };

export type ReadingViewProps = {
  reading: ReadingViewData;
  /** Defaults to `{ kind: 'original' }`. See rule 4. */
  prose?: ReadingProse;
  /**
   * Rendered under the disclaimer. V7's `ShareFooter` and `TryItYourself` go
   * here; `/history` passes nothing.
   *
   * A `ReactNode` rather than a boolean flag, so this component never learns
   * that sharing exists.
   */
  footer?: ReactNode;
  /** Fires when the card-detail overlay opens. Both mounts want an event and the
   *  two event names differ, so the name is the caller's to choose. */
  onCardOpened?: (card: ReadingViewCard) => void;
};

/**
 * RULE 4, IN ONE FUNCTION. Read it before changing anything here.
 *
 * The order of the branches is the whole contract:
 *
 *   1. No stored body at all -> `unavailable`, whatever the caller said. A
 *      `failed` reading has nothing to translate and asking V2 to translate null
 *      is a request that can only fail.
 *   2. The caller supplied a translation -> use it.
 *   3. The prose language matches the viewer -> the original.
 *   4. Otherwise -> `translating`, NEVER the original. A caller who forgot gets
 *      a spinner, not an Indonesian paragraph in an English app.
 */
function resolveProse(
  reading: ReadingViewData,
  prose: ReadingProse | undefined,
  viewer: Locale,
): ReadingProse {
  if (reading.body === null || reading.body.trim() === '') return { kind: 'unavailable' };
  if (prose && prose.kind !== 'original') return prose;
  if (reading.locale === viewer) return { kind: 'original' };
  return { kind: 'translating', text: '' };
}

export function ReadingView({ reading, prose, footer, onCardOpened }: ReadingViewProps) {
  const t = useT();
  /** Index into `reading.cards` of the open overlay, if any. */
  const [detail, setDetail] = useState<number | null>(null);

  const reader = readerById(reading.readerId);
  const service = serviceById(reading.serviceId);
  /*
   * A reader or service id that no longer exists is a 404's worth of missing
   * data, not a crash. It can only happen if someone removes a reader while rows
   * referencing it are in the table, and rendering nothing beats throwing inside
   * a page that has already sent its headers.
   */
  if (!reader || !service) return null;

  const labels = slotLabels(service, reader, t.locale);
  /*
   * SORTED BY `position`, NOT BY ARRAY ORDER. The query orders by position and
   * so does the API, but this object also arrives from V7's resolver and from a
   * future post-reading mount, and a spread rendered in insert order is the
   * quiet version of the bug that once showed one hand and read another.
   */
  const ordered = [...reading.cards].sort((a, b) => a.position - b.position);
  const draws: Draw[] = ordered.flatMap((c) => {
    const card = cardById(c.cardId);
    return card ? [{ card, reversed: c.reversed }] : [];
  });

  const shown = resolveProse(reading, prose, t.locale);
  const openCard = detail !== null ? ordered[detail] : undefined;
  const openDraw = detail !== null ? draws[detail] : undefined;

  return (
    <article className={styles.view}>
      <header className={styles.head}>
        <h1 className={styles.service}>{service.name[t.locale]}</h1>
        <p className={styles.meta}>
          {reader.name}
          {' · '}
          {formatLocalDate(reading.localDate, t.locale, true)}
          {' · '}
          {formatTime(new Date(reading.createdAtIso), t.locale)}
        </p>
      </header>

      {reading.question ? (
        <div className={styles.questionBlock}>
          <div className={styles.questionLabel}>{t('history.detail.question')}</div>
          {/*
            RENDERED AS TEXT, NEVER AS AN INPUT. An editable field here would
            imply the reading could be re-asked, which VD14 says it cannot.
          */}
          <p className={styles.question}>{reading.question}</p>
        </div>
      ) : null}

      {/*
        `showFaces` and NO `boxRefs`. The fan is what normally animates a card
        into a slot, and there is no fan here, so the slot has to draw the face
        itself -- the same branch the reduced-motion path already uses.
      */}
      <Slots labels={labels} picks={draws} showFaces />

      {/*
        A separate tap layer over the slot row, because `Slots` renders boxes and
        not buttons. One button per drawn card, sized to the box, absolutely
        positioned by the same flex row -- see the CSS. Keeping `Slots` free of
        an onTap prop means the draw screen's own tap handling stays where it is.
      */}
      <div className={styles.taps}>
        {draws.map((d, i) => (
          <button
            key={`${d.card.id}-${i}`}
            type="button"
            className={styles.tap}
            aria-label={t('draw.card.aria.picked', { slot: i + 1, name: d.card.name })}
            onClick={() => {
              setDetail(i);
              const c = ordered[i];
              if (c) onCardOpened?.(c);
            }}
          />
        ))}
      </div>

      {/*
        H4. FROM `readings.verdict`, THROUGH THE CATALOG, NEVER FROM THE PROSE.
        `effectiveYesNo()` decided this at draw time and it is the one fact about
        a yes/no reading that survives translation untouched.
      */}
      {reading.verdict ? (
        <div className={styles.verdict}>{t(`reading.verdict.${reading.verdict}` as const)}</div>
      ) : null}

      <section className={styles.prose} aria-live={shown.kind === 'translating' ? 'polite' : 'off'}>
        {shown.kind === 'original' ? <p className={styles.body}>{reading.body}</p> : null}

        {shown.kind === 'translated' ? <p className={styles.body}>{shown.text}</p> : null}

        {shown.kind === 'translating' ? (
```

## 4. `/history` — the list

### 4.1 Why the page reads nothing

Roadmap §1's fourth non-negotiable: *"Nothing new goes on the render path.
`/account` and `/history` are new pages with new queries; they inherit §6 of the
v0.2.0 roadmap exactly."*

There is a second reason and it is the decisive one. **The default filter is
today in the querent's timezone, and the server does not know it.** `todayKey()`
exists precisely because `toISOString()` rolls over at 07:00 in Jakarta. A
server-rendered list defaulting to the server's UTC date would show yesterday's
readings to a third of every Jakarta evening — the same bug `local_date` was
introduced to prevent, reintroduced in the one place a user would definitely
notice.

So `src/app/history/page.tsx` renders the title, the hint and a `<HistoryBrowser />`,
and awaits nothing but `getT()`.

### 4.2 The hydration trap this creates

**`todayKey()` must never run during render.** It reads `new Date()`, which is a
different value on the server and on the client, and React cannot patch
attribute mismatches during hydration — the same class of failure as
`shuffleDeck()` in a `useState` initialiser, recorded in `CLAUDE.md`, where the
DOM kept the server's cards and state held the client's.

`HistoryBrowser` therefore starts with `today = null` and `selected = null`,
renders the filter shell and nothing else, and sets both in an effect. Nothing
flashes, because there was never any content to replace.

### 4.4 `src/app/history/HistoryBrowser.tsx`

```tsx
'use client';

/**
 * The date filter and the day's list.
 *
 * `todayKey()` IS NOT CALLED DURING RENDER, and this is the whole shape of the
 * component. It reads `new Date()`, which differs between the server render and
 * the client hydration, and React cannot patch a mismatch -- the same trap as
 * `shuffleDeck()` in a `useState` initialiser (CLAUDE.md). So `today` starts null,
 * an effect sets it, and everything downstream waits. Nothing flashes because
 * there is nothing to replace.
 *
 * TWO REQUESTS ON MOUNT, IN PARALLEL: the days that have readings (once, for the
 * filter strip) and the selected day's items (again on every filter change). Both
 * are indexed reads of the querent's own rows; neither is rate limited (H12).
 */
import { useCallback, useEffect, useRef, useState } from 'react';
import { DateFilter } from './DateFilter';
import { HistoryItemRow } from './HistoryItemRow';
import { SESSION_HEADER } from '@/lib/analytics/localdate';
import { getSessionId, track } from '@/lib/analytics/track.client';
import { dayOffset, isHistoryDate } from '@/lib/history/dates';
import { useT } from '@/lib/i18n/LocaleProvider';
import { formatLocalDate } from '@/lib/i18n/format';
import { todayKey } from '@/lib/storage';
import type { HistoryItem } from '@/lib/history/types';
import styles from './HistoryBrowser.module.css';

type Load = { status: 'idle' } | { status: 'ok'; items: HistoryItem[] } | { status: 'error' };

export function HistoryBrowser() {
  const t = useT();
  const [today, setToday] = useState<string | null>(null);
  const [selected, setSelected] = useState<string | null>(null);
  const [days, setDays] = useState<string[] | null>(null);
  const [load, setLoad] = useState<Load>({ status: 'idle' });
  /** StrictMode double-invokes effects; `history.viewed` must fire once. */
  const viewedFired = useRef(false);

  // Step 1: learn what day it is, on the client, once.
  useEffect(() => {
    const now = todayKey();
    const q = new URL(window.location.href).searchParams.get('date');
    setToday(now);
    setSelected(isHistoryDate(q, now) ? (q as string) : now);
  }, []);

  // Step 2: which days have anything. Fetched once; the strip is built from it.
  useEffect(() => {
    if (!today) return;
    const controller = new AbortController();
    (async () => {
      try {
        const res = await fetch('/api/history/days', {
          headers: { [SESSION_HEADER]: getSessionId() },
          signal: controller.signal,
        });
        if (!res.ok) return;
        const body = (await res.json()) as { days: string[] };
        setDays(body.days);
        if (!viewedFired.current) {
          viewedFired.current = true;
          track('history.viewed', {
            day_count: body.days.length,
            has_any: body.days.length > 0,
            /*
             * `document.referrer` is a URL and would be free text; the ORIGIN
             * comparison is a boolean dressed as an enum, which is rule 2 of the
             * taxonomy. V4's menu link is same-origin; a bookmark is not.
             */
            source: sameOrigin(document.referrer) ? 'menu' : 'direct',
          });
        }
      } catch {
        /* The list's own error state covers it; a dead days-strip is survivable. */
      }
    })();
    return () => controller.abort();
  }, [today]);

  // Step 3: the selected day's items. Re-runs on every filter change.
  useEffect(() => {
    if (!selected) return;
    const controller = new AbortController();
    setLoad({ status: 'idle' });
    (async () => {
      try {
        const res = await fetch(`/api/history?date=${encodeURIComponent(selected)}`, {
          headers: { [SESSION_HEADER]: getSessionId() },
          signal: controller.signal,
        });
        if (!res.ok) {
          setLoad({ status: 'error' });
          return;
        }
        const body = (await res.json()) as { items: HistoryItem[] };
        setLoad({ status: 'ok', items: body.items });
      } catch (err) {
        // An abort is a normal path (StrictMode, and every filter change).
        if (!controller.signal.aborted) setLoad({ status: 'error' });
      }
    })();
    return () => controller.abort();
  }, [selected]);

  const choose = useCallback(
    (date: string, via: 'chip' | 'picker') => {
      if (!today) return;
      setSelected(date);
      track('history.filtered', {
        offset_days: dayOffset(today, date),
        had_readings: (days ?? []).includes(date),
        via,
      });
      /*
       * `replaceState`, NOT `router.replace` (H13). A Next navigation per chip
       * tap re-runs middleware and an RSC render to change a client-side filter.
       * This makes the URL shareable and reload-correct for free.
       */
      const url = new URL(window.location.href);
      url.searchParams.set('date', date);
      window.history.replaceState(null, '', url);
    },
    [days, today],
  );

  if (!today || !selected) return <div className={styles.shell} aria-busy="true" />;

  return (
    <div className={styles.shell}>
      <DateFilter today={today} selected={selected} days={days ?? []} onChoose={choose} />

      {load.status === 'error' ? <p className={styles.error}>{t('history.error')}</p> : null}

      {load.status === 'ok' && load.items.length > 0 ? (
        <>
          <p className={styles.count}>{t.plural('history.count', load.items.length, {})}</p>
          <ol className={styles.list}>
            {load.items.map((item) => (
              <HistoryItemRow key={item.id} item={item} today={today} />
            ))}
          </ol>
        </>
      ) : null}

      {load.status === 'ok' && load.items.length === 0 ? (
        <Empty selected={selected} days={days} onChoose={choose} />
      ) : null}
    </div>
  );
}

/**
 * H9 / §4.8. TWO EMPTY STATES, AND TELLING THEM APART IS THE POINT.
 *
 * A user who has never read must not be told "nothing on 27 July" -- that
 * sentence implies other days might have something and sends them looking. A
 * user who HAS read gets the nearest day they did, as one tap, because the most
 * likely reason for an empty today is that they read yesterday.
 */
function Empty({
  selected,
  days,
  onChoose,
}: {
  selected: string;
  days: string[] | null;
  onChoose: (date: string, via: 'chip' | 'picker') => void;
}) {
  const t = useT();

  if (days !== null && days.length === 0) {
    return (
      <div className={styles.empty}>
        <p className={styles.emptyTitle}>{t('history.empty.never.title')}</p>
        <p className={styles.emptyBody}>{t('history.empty.never.body')}</p>
        <a className={styles.emptyAction} href="/">
          {t('history.empty.never.action')}
        </a>
      </div>
    );
  }

  // `days` is sorted newest-first by the query, so the first one at or before the
  // selected day is the nearest earlier one; failing that, the most recent of all.
  const nearest = (days ?? []).find((d) => d < selected) ?? (days ?? [])[0] ?? null;

  return (
    <div className={styles.empty}>
      <p className={styles.emptyTitle}>
        {t('history.empty.day', { date: formatLocalDate(selected, t.locale, true) })}
      </p>
      {nearest ? (
        <button type="button" className={styles.emptyAction} onClick={() => onChoose(nearest, 'chip')}>
          {t('history.empty.nearest', { date: formatLocalDate(nearest, t.locale, true) })}
        </button>
      ) : null}
    </div>
  );
}

function sameOrigin(referrer: string): boolean {
  try {
    return new URL(referrer).origin === window.location.origin;
  } catch {
    return false;
  }
}
```

### 4.5 `src/app/history/DateFilter.tsx`

```tsx
'use client';

/**
 * The filter (H8). No dependency, and there must not be one -- VD17's argument
 * against a carousel library applies to a date picker with more force, because
 * the platform ships one.
 *
 * TWO CONTROLS, AND EACH DOES SOMETHING THE OTHER CANNOT:
 *
 *   - A scroll-snap strip of the days that ACTUALLY HAVE READINGS, newest first.
 *     Every chip is guaranteed non-empty, which is the thing a month grid cannot
 *     promise without a request per month. This is the control people will use.
 *   - A native `<input type="date">`, bounded by the first reading and today, for
 *     jumping to a specific old date. On iOS this is the system wheel, which is
 *     better than anything we would build and costs nothing.
 *
 * TODAY IS ALWAYS THE FIRST CHIP, even when it has no readings. The default
 * selection must be visible and re-selectable; a strip whose selected item is not
 * in it reads as broken.
 */
import { DAY_CHIP_LIMIT } from '@/lib/history/dates';
import { formatLocalDate } from '@/lib/i18n/format';
import { useT } from '@/lib/i18n/LocaleProvider';
import styles from './DateFilter.module.css';

export function DateFilter({
  today,
  selected,
  days,
  onChoose,
}: {
  today: string;
  selected: string;
  days: string[];
  onChoose: (date: string, via: 'chip' | 'picker') => void;
}) {
  const t = useT();

  /*
   * Today, then every day with readings, deduped, then the selected day if the
   * user reached an empty one through the picker. Order is preserved, so the
   * strip stays newest-first.
   */
  const chips = [...new Set([today, ...days, selected])]
    .sort((a, b) => (a < b ? 1 : a > b ? -1 : 0))
    .slice(0, DAY_CHIP_LIMIT);

  const thisYear = today.slice(0, 4);

  return (
    <div className={styles.filter}>
      <div className={styles.strip} role="group" aria-label={t('history.filter.aria')}>
        {chips.map((day) => (
          <button
            key={day}
            type="button"
            className={`${styles.chip}${day === selected ? ` ${styles.on}` : ''}${
              days.includes(day) ? '' : ` ${styles.bare}`
            }`}
            aria-pressed={day === selected}
            onClick={() => onChoose(day, 'chip')}
          >
            {day === today
              ? t('history.filter.today')
              : /* The year only when it is not this one -- otherwise every chip
                   carries four redundant characters on a 390px strip. */
                formatLocalDate(day, t.locale, day.slice(0, 4) !== thisYear)}
          </button>
        ))}
      </div>

      <label className={styles.pickerRow}>
        <span className={styles.pickerLabel}>{t('history.filter.label')}</span>
        <input
          type="date"
          className={styles.picker}
          value={selected}
          /* `days` is newest-first, so the last entry is the oldest reading. */
          min={days.length > 0 ? days[days.length - 1] : today}
          max={today}
          onChange={(e) => {
            const v = e.target.value;
            if (v) onChoose(v, 'picker');
          }}
        />
      </label>
    </div>
  );
}
```

### 4.8 H9 — what an empty day shows, and why it is not M14

`DaySummary` and `FrequencyLine` render **nothing** when there is nothing, and
`CLAUDE.md` records the reason: *"an empty state announces that the feature exists
and that this user has not earned it."* Both are **ambient** — the querent did not
ask for them, so silence costs nothing and speaking costs the illusion.

**History is not ambient. The querent tapped a menu item called History.** Silence
there is not tact, it is a broken page: no title, no list, no explanation,
nothing to do next. So it gets copy — and it gets **two** different copies,
because conflating them produces a lie:

- **They have read before, just not on this day.** *"Tidak ada bacaan pada 27 Juli."*
  plus a button to the nearest day that does have one. The most likely reason
  today is empty is that they read yesterday, and the days-query already knows
  which day that was, so the dead end becomes one tap. This is where the
  "which days have readings" query earns its keep a second time.
- **They have never read at all.** A different string and a link to the reader
  picker. Telling a first-time visitor *"nothing on 27 July"* implies other days
  might have something and sends them hunting through an empty calendar.

The two are distinguished by `days.length === 0`, which costs nothing because the
strip needs the array anyway.

Neither string is an accusation and neither is a count. *"Kamu belum pernah
membaca"* is a statement of fact about the app, not a judgement about the user,
and the CTA is the thing to do about it.

## 5. `/history/[id]` — the detail

### 5.1 Why this one DOES read on the render path

H7. The reading is the page's entire content: there is no chrome worth painting
first, nothing arrives later, and the query is a primary-key lookup with a
`user_id` predicate. Mounting empty and fetching would trade a sub-millisecond
server read for a round trip, a loading state and a layout shift, to satisfy a
rule whose purpose is preventing exactly those.

This is the same allowance `/onboarding` takes ("the one authoritative read the
roadmap's first non-negotiable allows"), and it is the shape V7's `/s/[slug]`
must take too, since a public page has nothing to render before its content.

### 5.2 Routing note, worth writing down

`/history` is a **static** segment and `src/app/[reader]/[service]` is dynamic.
Next matches static segments first at every level, so `/history` and
`/history/<uuid>` resolve to the new routes and never fall through to
`readerById('history')`. This is the same neighbourhood as the `_`-prefixed
private-folder trap `CLAUDE.md` records, and the failure if it were wrong would
be a 404 on a page that plainly exists.

```tsx
'use client';

/**
 * The thin client wrapper that owns the TRANSLATION and nothing else.
 *
 * WHY IT EXISTS AT ALL: `ReadingView` takes prose as data (H2) so V7 can mount it
 * on a page with no session, and a streaming translation needs client state. This
 * file is that state, and it is deliberately the only thing in it -- everything
 * visual is in `ReadingView`, which is the point of VD10.
 */
import { useEffect, useRef, useState } from 'react';
import { ReadingView, type ReadingProse, type ReadingViewData } from '@/components/ReadingView';
import { SESSION_HEADER } from '@/lib/analytics/localdate';
import { getSessionId, track } from '@/lib/analytics/track.client';
import { useT } from '@/lib/i18n/LocaleProvider';

export function HistoryDetail({
  reading,
  cachedTranslation,
}: {
  reading: ReadingViewData;
  cachedTranslation: string | null;
}) {
  const t = useT();
  const needs = reading.locale !== t.locale && reading.body !== null;

  const [prose, setProse] = useState<ReadingProse>(() => {
    if (!needs) return { kind: 'original' };
    if (cachedTranslation) return { kind: 'translated', locale: t.locale, text: cachedTranslation };
    return { kind: 'translating', text: '' };
  });

  const started = useRef(false);

  useEffect(() => {
    if (!needs || cachedTranslation) return;
    // StrictMode mounts, unmounts and remounts. Each run here is a MODEL CALL.
    if (started.current) return;
    started.current = true;

    const controller = new AbortController();

    (async () => {
      try {
        const res = await fetch('/api/translate', {
          method: 'POST',
          headers: { 'content-type': 'application/json', [SESSION_HEADER]: getSessionId() },
          signal: controller.signal,
          body: JSON.stringify({
            entity: 'reading',
            entityId: reading.id,
            field: 'body',
            targetLocale: t.locale,
          }),
        });
        if (!res.ok || !res.body) {
          setProse({ kind: 'unavailable' });
          return;
        }

        const stream = res.body.pipeThrough(new TextDecoderStream()).getReader();
        let acc = '';
        for (;;) {
          const { done, value } = await stream.read();
          if (done) break;
          acc += value;
          /*
           * Set the accumulated string, never `setProse(p => …)`. StrictMode
           * double-invokes updaters and would duplicate every chunk in
           * development -- the same trap `DaySummary` records.
           */
          setProse({ kind: 'translating', text: acc });
        }
        setProse(
          acc.trim()
            ? { kind: 'translated', locale: t.locale, text: acc }
            : { kind: 'unavailable' },
        );
      } catch {
        if (!controller.signal.aborted) setProse({ kind: 'unavailable' });
      }
    })();

    return () => controller.abort();
  }, [needs, cachedTranslation, reading.id, t.locale]);

  return (
    <ReadingView
      reading={reading}
      prose={prose}
      onCardOpened={(c) =>
        track('draw.card_detail_opened', {
          card_id: c.cardId,
          reversed: c.reversed,
          slot: c.position,
          /*
           * FALSE, AND IT IS NOT A LIE. `during_reading` asks whether the stream
           * was live when the card was opened. In history it never is. Reusing
           * the existing event rather than minting a tenth name keeps
           * "how often does anyone look at a card properly" one query.
           */
          during_reading: false,
        })
      }
    />
  );
}
```

## 6. The queries

All three go in `src/lib/db/queries/history.ts`, which W4 already owns for
`insertReading` and W5 for `recallableReadings`. **Every one takes `db` first**
(`queries/contract.test.ts` rule 1). None imports `../client`.

### 6.1 Why the list does not select `body`

H10. Three reasons, in ascending order of how much they matter: it is kilobytes
per row for text nothing renders; it means the API response cannot accidentally
be logged with a reading in it; and — the binding one — **the list payload lands
in the browser, and shipping Indonesian prose into an English client is what VD8
forbids.** `hasBody` is the boolean the row actually needs, computed in SQL as
`body is not null`.

### 6.2 Why `blocked` is filtered and nothing else is

`readingsOnDay`'s header argues the opposite for the day summary — *"a day summary
is a COUNT and a shape of the day: 'you drew three times today' is true whether or
not the third finished"* — and it is right about a summary. It is wrong about a
list you can open.

- **`blocked` is hidden.** Reconciliation R7 says a blocked reading writes **no
  card rows**. There is no draw, so there is nothing to reconstruct and the
  feature's whole premise fails on that row. It is also the one row whose
  `question` column holds text W7's classifier flagged as harmful; W7 redacts the
  same words from `moderation_flags` after 30 days, and a permanent browsable copy
  under a different column name would quietly undo that.
- **`failed` and `aborted` are shown.** The querent drew those cards, and
  reconciliation R7 already counts them toward the frequency verdict. A History
  that hides a draw the frequency feature counted makes two features disagree
  about the same past — which is precisely the class of failure the memory
  workstream exists to avoid. They render with a *"this reading did not finish"*
  line and no retry (VD14).
- **`partial` is shown as normal.** It has real prose; the `[Bacaan terputus…]`
  notice deliberately never reached `readings.body`.

`recallableReadings`'s five filters are stricter still, and correctly: a callback
needs something quotable. This one needs something *drawable*.

### 6.3 The three functions

Appended to `src/lib/db/queries/history.ts`:

```ts
/**
 * ONE DAY'S READINGS, FOR THE HISTORY LIST (V6).
 *
 * ONE FILTER, `status <> 'blocked'`, and it is deliberately neither
 * `readingsOnDay`'s none nor `recallableReadings`'s five. A blocked reading has
 * NO CARD ROWS (reconciliation R7), so there is no draw to reconstruct -- and its
 * `question` is text W7 classified as harmful, which W7 redacts from
 * `moderation_flags` at 30 days and which must not outlive that under another
 * column name. `failed` and `aborted` stay: the querent drew those cards, R7
 * already counts them in the frequency verdict, and hiding them here would make
 * two features disagree about the same past.
 *
 * NO `body` AND NO `gist` IN THE SELECT. `hasBody` is computed in SQL. The list
 * payload reaches the browser, and prose in a language the viewer is not reading
 * is what VD8 forbids -- whether or not anything renders it.
 *
 * Served by `readings_user_local_date_idx`. Ordered `created_at desc, id desc`:
 * `created_at` defaults to `now()`, which is TRANSACTION-START time, so two rows
 * written in one transaction share a timestamp exactly and `created_at desc`
 * alone is not a total order. Production never hits it; `withRollback` hits it on
 * every integration run. Same tiebreak, same reason, as `recallableReadings`.
 */
export type HistoryItem = {
  id: string;
  readerId: ReaderId;
  serviceId: ServiceId;
  localDate: string;
  /** ISO 8601. A string so the RSC path and the JSON path carry one shape. */
  createdAtIso: string;
  locale: Locale;
  status: ReadingStatus;
  verdict: YesNo | null;
  question: string | null;
  hasBody: boolean;
  sharedAt: string | null;
  cards: { cardId: number; reversed: boolean; position: number }[];
};

export async function readingsForDay(
  db: DbOrTx,
  userId: string,
  localDate: string,
): Promise<HistoryItem[]> {
  const rows = await db
    .select({
      id: readings.id,
      readerId: readings.readerId,
      serviceId: readings.serviceId,
      localDate: readings.localDate,
      createdAt: readings.createdAt,
      locale: readings.locale,
      status: readings.status,
      verdict: readings.verdict,
      question: readings.question,
      hasBody: sql<boolean>`${readings.body} is not null`,
      sharedAt: readings.sharedAt,
    })
    .from(readings)
    .where(
      and(
        eq(readings.userId, userId),
        eq(readings.localDate, localDate),
        ne(readings.status, 'blocked'),
      ),
    )
    .orderBy(desc(readings.createdAt), desc(readings.id));

  if (rows.length === 0) return [];

  const cards = await db
    .select({
      readingId: readingCards.readingId,
      cardId: readingCards.cardId,
      reversed: readingCards.reversed,
      position: readingCards.position,
    })
    .from(readingCards)
    .where(inArray(readingCards.readingId, rows.map((r) => r.id)))
    .orderBy(readingCards.position);

  const byReading = new Map<string, HistoryItem['cards']>();
  for (const c of cards) {
    const list = byReading.get(c.readingId);
    const entry = { cardId: c.cardId, reversed: c.reversed, position: c.position };
    if (list) list.push(entry);
    else byReading.set(c.readingId, [entry]);
  }

  return rows.map((r) => ({
    id: r.id,
    readerId: r.readerId as ReaderId,
    serviceId: r.serviceId as ServiceId,
    localDate: r.localDate,
    createdAtIso: r.createdAt.toISOString(),
    locale: r.locale as Locale,
    status: r.status as ReadingStatus,
    verdict: r.verdict as YesNo | null,
    question: r.question,
    hasBody: Boolean(r.hasBody),
    sharedAt: r.sharedAt ? r.sharedAt.toISOString() : null,
    cards: byReading.get(r.id) ?? [],
  }));
}

/**
 * THE DAYS THAT HAVE READINGS, newest first. The filter strip is built from this.
 *
 * WHY THIS QUERY EXISTS RATHER THAN A MONTH GRID: a calendar that offers 365 days
 * of which four have anything is a control that mostly wastes taps. Every chip
 * this returns is guaranteed non-empty, and the same array answers the empty-day
 * screen's "your nearest reading was..." with no second request.
 *
 * `select distinct local_date ... order by local_date desc limit $2` walks
 * `readings_user_local_date_idx` in reverse and stops at the limit, so a user
 * with five thousand readings pays for `limit` distinct values and not for five
 * thousand rows. Same `status <> 'blocked'` filter as the list, or the strip
 * would offer a day whose only reading the list refuses to show.
 */
export async function historyDays(
  db: DbOrTx,
  userId: string,
  limit: number,
): Promise<string[]> {
  if (limit <= 0) return [];
  const rows = await db
    .selectDistinct({ localDate: readings.localDate })
    .from(readings)
    .where(and(eq(readings.userId, userId), ne(readings.status, 'blocked')))
    .orderBy(desc(readings.localDate))
    .limit(limit);
  return rows.map((r) => r.localDate);
}

/**
 * ONE READING, WITH ITS CARDS AND ITS PROSE. The detail screen's whole payload.
 *
 * `userId` IS A PREDICATE, NOT AN ASSERTION MADE AFTERWARDS. Fetching by id and
 * then comparing owners in JavaScript is one forgotten `if` away from serving a
 * stranger's reading, and the forgotten `if` is invisible in review. Making
 * ownership part of the `where` means the only failure mode is a null.
 *
 * Null covers "does not exist", "belongs to someone else" and "was blocked" with
 * one value, and the caller 404s all three identically. That is deliberate and it
 * is the same rule V7 needs for share slugs: a distinguishable "exists but is not
 * yours" turns a uuid guess into an existence oracle.
 */
export type ReadingDetail = Omit<HistoryItem, 'hasBody'> & { body: string | null };

export async function readingWithCards(
  db: DbOrTx,
  userId: string,
  readingId: string,
): Promise<ReadingDetail | null> {
  /*
   * A malformed uuid must be a null, not a driver error. Postgres raises
   * `22P02 invalid input syntax for type uuid` on `where id = 'banana'`, and an
   * unhandled one here would 500 a page that should 404 -- and would put the
   * failing statement in the platform log.
   */
  if (!UUID_RE.test(readingId)) return null;

  const [row] = await db
    .select()
    .from(readings)
    .where(
      and(
        eq(readings.id, readingId),
        eq(readings.userId, userId),
        ne(readings.status, 'blocked'),
      ),
    )
    .limit(1);
  if (!row) return null;

  const cards = await db
    .select({
      cardId: readingCards.cardId,
      reversed: readingCards.reversed,
      position: readingCards.position,
    })
    .from(readingCards)
    .where(eq(readingCards.readingId, row.id))
    .orderBy(readingCards.position);

  return {
    id: row.id,
    readerId: row.readerId,
    serviceId: row.serviceId,
    localDate: row.localDate,
    createdAtIso: row.createdAt.toISOString(),
    locale: row.locale,
    status: row.status,
    verdict: row.verdict,
    question: row.question,
    body: row.body,
    sharedAt: row.sharedAt ? row.sharedAt.toISOString() : null,
    cards,
  };
}

/** Version 1-8, variant 8/9/a/b. Mirrors `validSessionId`'s pattern in
 *  `src/lib/analytics/localdate.ts`, for the same reason: keep junk out of an
 *  indexed comparison and out of the driver's error path. */
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[1-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i;
```

### 6.4 No new index, and why that is a decision

`readings_user_local_date_idx` on `(user_id, local_date)` serves `readingsForDay`
and `historyDays`; `readingWithCards` is a primary-key lookup;
`reading_cards_reading_idx` serves both card fetches. **Adding an index here would
be write amplification for nothing**, which is the argument `schema.ts` already
makes against `(user_id, card_id)`. Ordering within a day is done in memory over
a handful of rows.

### 6.5 `src/lib/history/dates.ts` — pure, and why it is not in `queries/`

`queries/contract.test.ts` requires the handle as the first parameter of every
exported function in `src/lib/db/queries/**`, and a date validator has no handle
to take. This is the same wall W3 hit with the Lotus cache and W5 hit with
`windowBounds` — and both resolved it the same way, so this does too. The module
is isomorphic (the route validates, the browser pre-checks `?date=`) and imports
nothing.

```ts
/**
 * Dates for the history filter. PURE, isomorphic, no imports.
 *
 * **DO NOT REUSE `parseLocalDate` FROM `src/lib/analytics/localdate.ts` HERE.**
 * That function bounds its input to +/-1 day around the server's UTC date,
 * because it answers "is this plausibly the querent's TODAY". A history filter's
 * whole job is to ask about days that are not today, so that bound would reject
 * every interesting request -- and it would do it as a 400 that looks like a
 * client bug. Same column, same format, opposite question.
 */

/** The chips the strip will render. Beyond this the native picker takes over. */
export const DAY_CHIP_LIMIT = 120;

/** How many distinct days `historyDays` will return. Roughly a year of daily use. */
export const HISTORY_DAY_LIMIT = 400;

/** Nothing in this app predates the rewrite; the floor only keeps `0001-01-01`
 *  out of an indexed comparison. */
const FLOOR = '2000-01-01';
const SHAPE = /^\d{4}-\d{2}-\d{2}$/;

/**
 * A real calendar day, not in the future.
 *
 * THE ROUND TRIP, NOT JUST `isNaN`, for the reason `parseLocalDate` records:
 * `new Date('2026-02-30T00:00:00Z')` silently normalises to March 2nd, so only
 * re-formatting and comparing catches it -- and it catches `2026-13-01` too.
 */
export function isHistoryDate(raw: unknown, today: string): raw is string {
  if (typeof raw !== 'string' || !SHAPE.test(raw)) return false;
  const parsed = new Date(`${raw}T00:00:00Z`);
  if (Number.isNaN(parsed.getTime()) || parsed.toISOString().slice(0, 10) !== raw) return false;
  return raw >= FLOOR && raw <= today;
}

/**
 * Whole days between two `'YYYY-MM-DD'` strings; positive means `date` is in the
 * past.
 *
 * THIS IS THE ONE PLACE `new Date('YYYY-MM-DD')` IS CORRECT, and it looks exactly
 * like the bug `local_date` exists to prevent -- so: both operands are parsed
 * into the SAME fiction (UTC midnight) and only the DIFFERENCE is used. No
 * instant is rendered, no zone is consulted, and the answer is identical in every
 * timezone on earth. Rendering either side would be the bug.
 */
export function dayOffset(today: string, date: string): number {
  const a = new Date(`${today}T00:00:00Z`).getTime();
  const b = new Date(`${date}T00:00:00Z`).getTime();
  return Math.round((a - b) / 86_400_000);
}
```

### 6.6 The two API routes

`src/app/api/history/route.ts`:

```ts
/**
 * One day of history, as metadata (H10). No prose, ever, in this response.
 *
 * NO `withAnalytics` AND NO RATE LIMIT, both on purpose. All three history events
 * fire from the client (H11) because `history.filtered` needs to know
 * chip-vs-picker and the server cannot; and `src/lib/ratelimit.ts`'s budget is
 * sized for model calls, so charging a scroll against it would make browsing your
 * own past cost you a reading (H12).
 */
import { NextResponse } from 'next/server';
import { requireUser } from '@/lib/auth/server';
import { db } from '@/lib/db/client';
import { readingsForDay } from '@/lib/db/queries/history';
import { isHistoryDate } from '@/lib/history/dates';
import { LOCAL_DATE_HEADER, parseLocalDate } from '@/lib/analytics/localdate';

export const runtime = 'nodejs';

export async function GET(request: Request) {
  const auth = await requireUser();
  if (!auth.ok) return auth.response;

  /*
   * `parseLocalDate` IS USED FOR *TODAY* AND `isHistoryDate` FOR THE FILTER, and
   * the split is the point. The header answers "what day is it where the querent
   * is" and its +/-1 bound is right for that; the query parameter asks about the
   * past, where that bound would reject every interesting request. See
   * `src/lib/history/dates.ts`.
   */
  const today = parseLocalDate(request.headers.get(LOCAL_DATE_HEADER)).date;
  const date = new URL(request.url).searchParams.get('date');
  if (!isHistoryDate(date, today)) {
    return NextResponse.json({ error: 'bad date' }, { status: 400 });
  }

  try {
    const items = await readingsForDay(db, auth.user.id, date);
    return NextResponse.json({ items }, { headers: { 'cache-control': 'private, no-store' } });
  } catch (err) {
    logFailure(err);
    return NextResponse.json({ error: 'unavailable' }, { status: 503 });
  }
}

/**
 * NEVER LOG THE DRIVER ERROR IN PRODUCTION (CLAUDE.md, twice: `flush.ts` and the
 * moderation path). A postgres error quotes the failing statement AND its bound
 * parameters, and `readings.question` is selected by the query above -- so a bare
 * `console.error(err)` here puts the querent's typed question into the platform
 * log. Development prints everything, because there is nobody to leak it to.
 */
function logFailure(err: unknown): void {
  if (process.env.NODE_ENV === 'development') console.error('[history] list failed', err);
  else console.error('[history] list failed', { name: err instanceof Error ? err.name : typeof err });
}
```

`src/app/api/history/days/route.ts` is the same shape around
`historyDays(db, user.id, HISTORY_DAY_LIMIT)` and returns `{ days: string[] }`.

## 7. Translation at the point of open (VD8)

**The list never translates. The detail translates once, on open, and never in
bulk.** A user with 200 readings who taps `EN` triggers zero model calls; opening
one Indonesian reading triggers one, and the second open triggers none because
V2's route upserts a `translations` row and §5.3 reads it back on the server.

The sequence:

1. `/history/[id]` compares `readings.locale` with `await getLocale()`.
2. Same → `ReadingView` gets `prose` omitted and renders `reading.body`.
3. Different, and a `translations` row exists → the server passes it as
   `cachedTranslation`; `HistoryDetail` seeds `{ kind: 'translated' }`.
   **No spinner, no flash, no request.**
4. Different, no row → `HistoryDetail` seeds `{ kind: 'translating', text: '' }`
   and POSTs `/api/translate`. `ReadingView` shows the pulsing
   `history.translating` eyebrow — the same treatment `ReadingPanel` gives a
   reading it is waiting for — and then streams the tokens into the same `<p>`.
5. The call fails → `{ kind: 'unavailable' }`, which renders
   `history.detail.noBody`'s sibling copy. **It never falls back to the original.**
   An Indonesian paragraph appearing in the English app because a translation
   failed is the exact outcome V2 exists to prevent, and a fallback is how it
   would happen.

Everything except the prose is already localized: service names and slot labels
are `Localized<>` in the data files, the date goes through `formatLocalDate`, the
verdict through the catalog. That is VD8's "what is actually rendered in a list is
metadata which the message catalog already localizes", made literal.

## 8. The traps this workstream will otherwise walk into

Each of these produces a working-looking page.

- **`todayKey()` DURING RENDER IS A HYDRATION BUG.** It reads `new Date()`, which
  differs between the server render and the client hydration, and React cannot
  patch attribute mismatches — the DOM keeps the server's day while state holds
  the client's. Same class as `shuffleDeck()` in a `useState` initialiser.
  `HistoryBrowser` starts `today` and `selected` at `null` and sets them in an
  effect. **Do not "simplify" that into `useState(() => todayKey())`.**

- **`parseLocalDate` MUST NOT VALIDATE THE FILTER.** Its ±1-day bound answers "is
  this plausibly today"; a history filter's entire job is days that are not today.
  Reusing it makes every date older than yesterday a 400 that reads as a client
  bug. Two functions, two questions — §6.5 has both.

- **A CLIENT COMPONENT MAY NOT `import type` FROM `@/lib/db/**`.**
  `src/lib/clientBoundary.test.ts`'s regex is
  `(?:from|import)\s+['"]([^'"]+)['"]` and does not know about the `type` keyword,
  so `import type { ReadingStatus } from '@/lib/db/schema'` fails a test that
  looks unrelated to the change. `ReadingStatus` moves to `src/data/types.ts` and
  the row shapes live in `src/lib/history/types.ts`.

- **NEVER LOG A DRIVER ERROR FROM A HISTORY ROUTE.** `readingsForDay` selects
  `readings.question`, so a postgres error quotes the querent's typed question in
  its bound parameters. Same rule and same reason as `flush.ts` and the moderation
  path; `logFailure` is copied from them deliberately rather than reinvented.

- **`order by created_at desc` ALONE IS NOT A TOTAL ORDER.** `created_at` defaults
  to `now()`, which is transaction-start time, so rows written in one transaction
  share a timestamp exactly. Production never hits it; `withRollback` hits it on
  every integration run, and W5's plan lost two tests to this. `desc(createdAt),
  desc(id)` in both list queries.

- **THE `blocked` FILTER IS SECURITY-ADJACENT, NOT COSMETIC.** Removing it puts
  W7-flagged question text into a permanently browsable list, at the same time as
  W7's sweep is deleting the same words from `moderation_flags`. If someone
  proposes showing blocked readings "for completeness", they are proposing undoing
  a retention promise.

- **A MALFORMED UUID IN THE PATH MUST 404, NOT 500.** `where id = 'banana'` raises
  SQLSTATE `22P02` from the driver, and an unhandled one both breaks the page and
  logs the statement. `readingWithCards` shape-checks before querying.

- **THE TAP LAYER'S GEOMETRY IS DUPLICATED FROM `Slots.module.css`.** 90×135, 12px
  gap, 78×117 and 8px below 359px. There is no test that can catch a drift,
  because catching it needs a browser and Chromium cannot launch in this image —
  so the numbers carry a comment in both files pointing at each other, and Task 17's
  harness reads `getBoundingClientRect` on both rows and asserts they coincide.

- **`/history` IS GATED AND MUST STAY GATED.** `isPublic()` does not name it and
  must not learn to. V7 makes a page public; this one is somebody's entire reading
  history and the only reason `requireUser()` is not in `page.tsx` is that
  middleware already ran.

3. **`formatTime` in `src/lib/i18n/format.ts` is a W6 file, and V2 and V8 may also
