## 1. Why this is the least glamorous workstream and the easiest one to fail

There is no clever part. There is one mechanism — a lookup — and then there is
a tree walk. The failure mode is not architectural; it is that somebody ships an
English app with three Indonesian strings left in it, and the three are in a
route handler nobody thought of as copy.

So the two things this plan spends its length on are (a) making a missing string
a **compile error** rather than a runtime `undefined` or a silent fallback, and
(b) an inventory exhaustive enough that "did we get them all" is answerable by
ticking boxes instead of by re-reading the tree. §7 is the checklist. It is the
most valuable page in this file.

The third thing, and the only one that is genuinely hard, is §9: the prompt
fork. An English fork of `base.ts` is not a translation job. Every format rule
in the Indonesian base contract was derived from a specific observed
misbehaviour of glm-4.6 — `**The Moon (Pulan) Terbalik**`, `Halo! Adrian siap
bantu.`, an emoji — and the English model's misbehaviours will not be the same
set. And the three worked-example paragraphs in `readers.ts` do more work than
every word of description around them. CLAUDE.md says so; the rewrite plan's
risk table says so; §10 of the roadmap says so again. A translated Margaret is
a translated Margaret. **Task 10 rewrites all three natively and is the single
highest-value task in this plan.**

### One thing D6 buys that is worth naming

Locale is **not** a URL segment. Therefore `generateStaticParams` on `[reader]`
and `[reader]/[service]` still yields nine combinations, not eighteen; there is
no `/en/...` tree to keep in sync; the middleware matcher does not grow a locale
prefix; and no link anywhere in the app has to be locale-aware. Every plan that
reaches for `useRouter().push('/en/...')` is wrong.

## 2. Decisions

Settled here. Raise a flag rather than relitigating.

| # | Decision | Choice | Why |
|---|---|---|---|
| I1 | Key shape | **Flat dotted keys**, `namespace.thing.variant`, `lowerCamelCase` segments | The type lock is one line (`Record<MessageKey, string>`) instead of a recursive `DeepKeys` helper, and the error message names the missing key instead of a whole subtree. Also: `grep -rn "reading.error.rateLimit" src` finds the definition and every call site, which is the property that matters when six other workstreams are writing copy. |
| I2 | Which catalog is authoritative | **`id.ts` defines the key set; `en.ts` is typed from it** | Indonesian is the default locale and the fallback of last resort, so it is the source language. A new key with no English is a red typecheck — the type error *is* the checklist. |
| I3 | Missing key at runtime | **Return the key string.** Never fall back to the other locale | A type-system bypass (`as any`, a dynamic key) must be *loud*. `reading.error.start` rendered on screen is a bug report; the Indonesian sentence rendered in the English app is a bug that ships. |
| I4 | Interpolation | `{name}` placeholders, params typed from the Indonesian message literal | `as const` on `id.ts` makes the message a literal type, so a template-literal type derives the required params. `t('nav.back.reader')` with a missing `{name}` is a compile error. |
| I5 | Pluralisation | **`Intl.PluralRules` + a `.one` / `.other` key family**, both categories declared in both catalogs | Indonesian does not inflect; English does. Hand-rolling `n === 1 ?` at the call site pushes that asymmetry into six workstreams' components. ICU MessageFormat would drag a parser into the client bundle for a handful of strings, against D6's "reviewable in a diff". |
| I6 | Indonesian plural families | Must declare `.one` and `.other` **identically**, enforced by a test | CLDR gives `id` only `other`, so `.one` is never selected. Declaring it keeps the key sets equal; asserting the two are identical stops anyone believing they edited something that renders. |
| I7 | Numbers and dates | `Intl.NumberFormat` inside `plural()`; a `formatDate()` helper that always uses `{day:'numeric', month:'long', year:'numeric'}` | Thousands separators differ (`1.000` vs `1,000`). A spelled month sidesteps the 26/7-vs-7/26 question entirely, so `en-GB` vs `en-US` never has to be decided. Locale map: `id → id-ID`, `en → en-GB`. |
| I8 | Server/client boundary | A pure `makeT(locale, messages)` in `format.ts`; `getT()` (async, server) and `useT()` (hook, client) both return it | One function that works in both is not possible in the App Router — the server one must `await headers()` and the client one must read context. What *is* identical is the **call site**: `t('draw.reset')` in both. Say that plainly rather than pretending otherwise. |
| I9 | Getting the locale to client components | **`LocaleProvider` in the root layout, given the already-resolved catalog** | No prop drilling and no double catalog in the bundle. The alternative — client imports both catalogs and picks — ships the locale the user did not choose, and grows every time a workstream adds copy. |
| I10 | Where the negotiation happens | **Once, in middleware**, forwarded as `x-jmt-locale` via `NextResponse.next({ request: { headers } })` | `Accept-Language` is parsed in exactly one place. Every server component then reads a header instead of redoing the chain. |
| I11 | Locale cookie | `jmt_locale`, `httpOnly`, `sameSite=lax`, `path=/`, one year | Nothing client-side needs to read it — the provider is handed the locale by the server. One less thing an injected script can see. |
| I12 | Dev locale override | `?lang=en`, honoured **only when `NODE_ENV !== 'production'`** | Screenshots via `tools/shot.sh` cannot set a cookie. There is precedent in the tree: `StillMode` reads `?still=1` the same way. Guarded by a test, because a production locale in a query string is a cache-poisoning shape and it would also quietly contradict D6. |
| I13 | The manifest | `manifest.ts` reads the **cookie** (not the header) and becomes dynamic | The manifest path is excluded from the middleware matcher, deliberately and correctly, so the header is not there. Cost is one uncached small JSON at install time, which is when the home-screen name is decided. |
| I14 | Where dual-role copy lives | **Copy used by both the UI and the prompt lives in the data files as `Localized<>`; UI-only copy lives in the catalog** | `positionFraming` is slot captions *and* prompt input. `service.name` is a heading *and* the `Layanan:` line. Splitting one of those across two systems guarantees they drift. Reader `bio` is UI-only but stays in `readers.json` for cohesion. |
| I15 | Long-form legal copy | **Not in the catalog.** `terms.id.tsx` / `terms.en.tsx`, selected by locale; only the chrome is keyed | A 2,000-word document as one catalog value is unreviewable in a diff. W7 owns the documents; the convention is fixed here. |
| I16 | The question delimiter | **`<pertanyaan>` in both locales** | It is a machine token, not copy. One token means one thing for `sanitize.ts` to strip and one thing to test, and an English querent will never type the word "pertanyaan" — whereas they will absolutely type "question". The English contract explains the tag; it does not need the model to know Indonesian. |
| I17 | Card names | **English in both locales. Non-negotiable.** | The artwork has the title rendered into the image. Unchanged from the iOS plan, the rewrite plan, `types.ts` and CLAUDE.md. |
| I18 | `cards.json` shape | Locale-keyed sub-objects: `keywords: Localized<string[]>`, `meaning: Localized<Pair>` | One file, one generator write, one import, one place a card's data lives. `Record<Locale, T>` makes a missing locale a compile error, which a `keywords_en` flat field cannot do. |
| I19 | `docs/seed-meanings.en.json` | **Deleted.** Its content becomes `MEANINGS_EN`'s starting point | It is a *generated artefact*, written by `generate_cards.py` from the ARCANA tuple's English seed columns. Once `MEANINGS_EN` exists there are two English tables and they will drift. Recoverable with `git show`. |
| I20 | `MAX_QUESTION_LENGTH` | **Stays 200 characters, one constant, both locales** | 200 chars is ~27 Indonesian words (avg 6.5 chars + space) and ~33 English words (avg 5.1). English gets *more* room, not less. A per-locale limit would be complexity bought with nothing. |
| I21 | Prompt fork shape | `base.id.ts` + `base.en.ts` behind an unchanged `base.ts` facade; same for `readers.ts` and `services.ts` | `build.ts` keeps importing three modules. A third locale is two files and one map entry. The facade also gives the fork a `Record<Locale, …>` type, so forgetting `en` is a compile error. |
| I22 | Order of the fork work | **Mechanical split first, proven byte-identical; English prose second** | Otherwise a persona regression hides inside a file move and nobody can tell which change caused it. Task 9 succeeds when the nine Indonesian system prompts are unchanged. Task 10 is the one that can go wrong on purpose. |
| I23 | Reading language vs question language | Both base contracts get an explicit rule: **write in the target language even if the question is in the other one** | Models mirror the input language. An English user typing an Indonesian question would get an Indonesian reading in an English app, and nobody would have written a rule against it. |
| I24 | `readings.locale` | Records the **UI locale at generation time**, not the language the question was typed in | It is the language the prose came out in. That is what history and the daily summary need to match on. |
| I25 | The switcher's DB write | Cookie and session are set on the response; `users.locale` goes through `after()` | Roadmap §6. A language toggle must not wait on Postgres. |
| I26 | English verdict words | `Yes` / `No` / **`Not yet`** | `Belum jelas` → "Not yet clear" reads fine as an opener but the smoke script's self-contradiction check greps for the *other* verdicts, and bare `No` collides with ordinary English prose. See Task 11 for how that check is downgraded for `en`. |

## 3. Schema deltas

`users.locale` and `readings.locale` are defined in roadmap §3 and are **not**
redefined here. Neither is `events.locale`, `daily_summaries.locale`, or
`lotus_avatars.summary_id` / `summary_en`. What follows is everything else.

**One new column, proposed to W7.**

```
moderation_flags
  locale              text            -- which locale's blocklist/classifier fired
```

Roadmap §4 says the blocklist is "deterministic patterns, per locale". Without
this column a flagged question cannot be traced back to the pattern set that
flagged it, and tuning the English list means guessing. Nullable, because the
classifier path may not have a locale in hand. W7's table, W7's call.

**One constraint, proposed to W1.**

```sql
alter table users add constraint users_locale_valid check (locale in ('id','en'));
```

And in `src/lib/db/schema.ts`, `locale` is declared
`text('locale').notNull().default('id').$type<Locale>()`, importing `Locale`
from `@/lib/i18n/locale`. The same `$type<Locale>()` on `readings.locale`,
`events.locale`, `daily_summaries.locale`. This is what stops a `'en-US'` or an
`'ID'` reaching the catalog lookup, where I3 would render raw keys at the user.

**One value convention on an existing column.**

`readings.prompt_version` (roadmap §3, `text not null`) is written as
`"<locale>-<n>"` — `id-1`, `en-1`, `id-2`. The Indonesian and English prompts
will be revised on different schedules, and a single integer would make an
English persona change look like an Indonesian one in the analytics. No schema
change; a format, fixed here, owed to W4.

**No new tables.** The catalogs are in the repo (D6). Nothing about a message
belongs in Postgres.

## 4. Interfaces I export

Six other workstreams write copy. All of them need `t()` and the key
convention. These signatures are the contract.

### `src/lib/i18n/locale.ts` — the leaf module

Deliberately dependency-free: no React, no `next/*`, no catalog import. It is
imported by `src/data/types.ts`, by the edge middleware, by
`generate_cards.py`'s output consumers and by `src/lib/db/schema.ts`, and any
one of those picking up a transitive React dependency would be a problem.

```ts
export const LOCALES = ['id', 'en'] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale = 'id';
export function isLocale(v: unknown): v is Locale;

/** A value that exists once per locale. A missing locale is a compile error. */
export type Localized<T> = Record<Locale, T>;

/** BCP-47 tag for Intl. `id -> id-ID`, `en -> en-GB` (see I7). */
export function intlTag(locale: Locale): string;
```

### `src/lib/i18n/locales/id.ts` — the source catalog

```ts
const id = {
  'app.title': 'JMTarot',
  'nav.back.reader': '← {name}',
  // ...
} as const satisfies Record<string, string>;

export default id;
export type MessageKey = keyof typeof id;
export type Catalog = Record<MessageKey, string>;
```

`as const satisfies Record<string, string>` is the whole trick. `as const` keeps
each value a string literal so I4's parameter derivation works; `satisfies`
checks the values are strings without widening the keys.

### `src/lib/i18n/locales/en.ts`

```ts
import type { Catalog } from './id';
const en: Catalog = { /* ... */ };
export default en;
```

A missing key is TS2739 ("is missing the following properties"). An extra key
is TS2353 (excess property check on an object literal against a declared type).
Both at `npm run typecheck`, both naming the key.

### `src/lib/i18n/format.ts` — pure, isomorphic, no `next/*`, no React

```ts
export type TParams = Record<string, string | number>;

/** Required params, derived from the Indonesian message's literal type. */
type Params<S extends string> =
  S extends `${string}{${infer P}}${infer Rest}`
    ? { [K in P]: string | number } & Params<Rest>
    : Record<never, never>;

type ParamsArg<K extends MessageKey> =
  Record<never, never> extends Params<(typeof id)[K]>
    ? [params?: TParams]
    : [params: Params<(typeof id)[K]>];

/** `foo.one` + `foo.other` in the catalog makes `foo` a plural key. */
type StripOne<K extends string> = K extends `${infer B}.one` ? B : never;
export type PluralKey = StripOne<MessageKey>;

export type TFunction = {
  <K extends MessageKey>(key: K, ...args: ParamsArg<K>): string;
  plural(key: PluralKey, count: number, params?: TParams): string;
  readonly locale: Locale;
};

export function catalogFor(locale: Locale): Catalog;
export function makeT(locale: Locale, messages: Catalog): TFunction;

/** Synchronous, explicit locale. For route handlers, `after()` callbacks,
 *  the smoke script, and anything outside a React render. */
export function tFor(locale: Locale): TFunction;

/** Always `{day:'numeric', month:'long', year:'numeric'}` — see I7. */
export function formatDate(d: Date, locale: Locale): string;
```

`plural(key, count)` selects `` `${key}.${new Intl.PluralRules(intlTag(locale)).select(count)}` ``
and injects `count`, pre-formatted with `Intl.NumberFormat`, into the params. So
`{count}` is available to the message without the caller passing it.

### `src/lib/i18n/resolve.ts` — server only

```ts
import 'server-only';

export const LOCALE_COOKIE = 'jmt_locale';
export const LOCALE_HEADER = 'x-jmt-locale';

/** Per-request memoized via React `cache()`. Reads the header middleware set,

export function resolveForMiddleware(
  req: NextRequest,
  sessionLocale: Locale | null,
): Locale;
```

## 5. Interfaces I need

### From W1 — data layer

1. `users.locale` declared `$type<Locale>()` from `@/lib/i18n/locale`, plus the
   check constraint in §3. Same for `readings.locale`, `events.locale`,
   `daily_summaries.locale`.
2. `setUserLocale(userId: string, locale: Locale): Promise<void>` in
   `src/lib/db/queries/profile.ts`. Called only from inside `after()`.

### From W2 — auth and session

This is the dependency that can break my resolution order, so it is spelled out.

1. **A `locale` claim on the JWT**, stamped from `users.locale` at sign-in.
   `resolve.ts` treats that claim as "the profile". Reading `users.locale` from
   Postgres on the render path would violate the roadmap's first
   non-negotiable, so "profile → cookie" operationally means "session claim →
   cookie".
2. `refreshSessionLocale(locale: Locale): Promise<void>` — re-signs the session
   cookie with a new claim, called by `POST /api/locale` **in the same
   response** as the cookie write. Without this, profile-beats-cookie means a
   stale claim instantly undoes every switch. See Open Question 1.
3. `readSessionLocale(req: NextRequest): Locale | null` — edge-safe, so
   middleware can feed `resolveForMiddleware`.
4. Four lines in `middleware.ts`, which W2 owns:

```ts
const locale = resolveForMiddleware(request, readSessionLocale(request));
const headers = new Headers(request.headers);
headers.set(LOCALE_HEADER, locale);
const res = NextResponse.next({ request: { headers } });
if (request.cookies.get(LOCALE_COOKIE)?.value !== locale) {
  res.cookies.set(LOCALE_COOKIE, locale, { httpOnly: true, sameSite: 'lax',
    path: '/', maxAge: 31_536_000, secure: process.env.NODE_ENV === 'production' });
}
return res;
```

   `NextResponse.next({ request: { headers } })` is the only form that mutates
   what downstream server components see. Setting a header on the plain
   response does nothing for RSC, and the symptom is `getLocale()` silently
   returning the cookie value forever.
5. `/api/locale` added to `isPublic()` in `middleware.ts`, next to `/login`. The
   login page carries a switcher and there is no session yet.
6. The login page's keys (`login.*`) move from the password form to the Google
   button, but the error keys survive in shape. W2 writes the Indonesian.

## 6. New environment variables

**One.**

```
LOCALE_SWITCHER=1     # render the language toggle. Unset = English reachable
                      # by cookie but not advertised in the UI.
```

Set in `.env.example` with the rest, and remember the rule that already bit this
project: **escape `$` as `\$` in `.env` files, never in the Vercel dashboard.**
This value has no `$` in it, but the next person copying the block will not know
that.

Why it exists: the six workstreams ship in parallel and the English readings are
the thing most likely to be unfinished on launch day. This flag lets the
interface work land without advertising a half-written Margaret. It controls
**rendering only** — it does not change the key set, does not change the
resolution order, and does not gate `en` behind a 404. A flag that changed the
key set would break the type guarantee, which is the one thing here worth
protecting.

### What is deliberately not an environment variable

`DEFAULT_LOCALE` is a constant in `src/lib/i18n/locale.ts`, not config. Every
string in the app falls back to it. A preview deployment that disagreed with
production about the default locale would be a bug nobody could reproduce
locally, and the upside — being able to flip the default without a commit — is
a thing we would want in a diff anyway.

The list of locales is likewise a constant. It is a union type; it cannot come
from the environment without giving up I2.

## 8. Resolution, surface by surface

The order is fixed by D6: **profile → cookie → `Accept-Language` → `'id'`**.
What that means in practice differs by where you are standing, and the
differences are the part that goes wrong.

```
                        ┌─────────────────────────────────────────────┐
  request ─────────────▶│ middleware.ts (edge, W2 owns the file)      │
                        │  resolveForMiddleware(req, sessionLocale)   │
                        │   1. session `locale` claim   ("profile")   │
                        │   2. jmt_locale cookie                      │
                        │   3. negotiate(Accept-Language)             │
                        │   4. DEFAULT_LOCALE                         │
                        │  + dev-only ?lang= override                 │
                        │  sets x-jmt-locale on the FORWARDED request │
                        │  refreshes the cookie if it disagreed       │
                        └──────────────────┬──────────────────────────┘
                                           │
        ┌──────────────────────────────────┼───────────────────────────────┐
        ▼                                  ▼                               ▼
  server components               route handlers                  manifest.ts
  await getLocale()               await getLocale()                cookies() only
  (header → cookie → default)     or tFor(locale)                  (matcher excludes it)
        │
        ▼
  root layout: <html lang={locale}>
               <LocaleProvider locale messages={catalogFor(locale)}>
                                 │
                                 ▼
                        client components: useT()
```

**Middleware.** The only place `Accept-Language` is parsed. `negotiate()` is a
pure function with its own tests: it splits on `,`, sorts by `q`, takes the
first tag whose primary subtag is a known locale, and returns `DEFAULT_LOCALE`
otherwise. `en-GB`, `en-US` and `en` all resolve to `en`; `id-ID` and `in` (the
deprecated ISO 639-1 code for Indonesian, which some Android browsers still
send) both resolve to `id`. That last one is worth a test — it is exactly the
sort of thing that fails silently for one class of device.

**Server components.** `await getLocale()`, memoized per request with React
`cache()` so a page that asks in three places pays once. It reads
`x-jmt-locale` first and falls back to the cookie, because the manifest route
and anything else outside the matcher will not have the header.

**The root layout.** Two consequences worth stating before someone notices them
in a build log:

1. `await getLocale()` in the root layout opts the whole tree into dynamic
   rendering. `generateStaticParams` on `[reader]` and `[reader]/[service]`
   still enumerates nine routes, but they render per-request. That is where
   this app is going anyway — W2 puts auth on every page, W5 puts a per-user
   daily summary on the reader picker — so this is paying early, not paying
   extra. The build output goes from ● to ƒ; that is expected, not a
   regression.
2. The alternative — keep `lang="id"` static and patch it on the client — is
   wrong. It ships the wrong language to a screen reader on first paint and it
   is wrong for the SSR'd markup that Next streams before hydration.

**Client components.** `LocaleProvider` sits in the root layout and is given the
resolved catalog. The catalog crosses the RSC boundary as JSON, once per full
page load, and is reused across client navigations within that layout. The
whole catalog goes, including keys the current page never reads — at a few
hundred short strings that is nothing. **If it ever stops being nothing**, the
escape hatch is to pass only the namespaces a subtree needs, keyed by the
namespace table in §4. Do not build that now.

The rule this replaces: no locale prop is drilled anywhere. If you find
yourself adding `locale` to a component's props, you either want `useT()` or
you are in a server component and want `getT()`.

**Route handlers.** `await getLocale()` works, but prefer `tFor(locale)` where
the locale is already in hand — in `/api/reading` it must be captured before
the stream opens (§7.9).

**What must never happen:** a client component importing `catalogFor()` and
picking a locale itself. That ships both catalogs. `format.ts` exports
`catalogFor` because the server needs it; the ESLint rule that fences
`@/lib/prompt/*` out of client files should fence this too.

### 9.2 The base contract in English is not a translation

Each rule in `BASE_CONTRACT` exists because glm-4.6 did the thing. The English
model will do a *different* set of things, so the English contract carries the
same rules re-derived, plus the ones English-language tarot writing invites.

| Rule | Indonesian origin | English form |
|---|---|---|
| No markdown | returned `**The Moon … Terbalik**` | same rule verbatim; re-verify — English chat models reach for `**` harder, not less |
| No emoji | returned an emoji | same rule |
| Card names exactly as given | invented `Pulan` for The Moon | **not vacuous in English.** The analogous failures are a parenthetical gloss (`The Moon (the card of illusion)`), lowercasing (`the moon`), and dropping the article (`Moon reversed`). The rule names all three. |
| No preamble | opened `Halo! Adrian siap bantu.` | same rule. English models greet at least as much. |
| No closing offer | — | **stronger in English.** "Let me know if you'd like me to go deeper" is close to reflexive in English assistant prose and will appear in every one of the nine. |
| Indonesian not Malay | the eleven-word grep | **replaced** by a register rule: plain contemporary English; no archaic diction (`thou`, `thy`, `'tis`) unless a persona calls for it; no capitalised abstractions (`the Universe`, `Divine Feminine`, `Source`); no vocatives (`dear one`, `beloved`, `sweet soul`). This is the English analogue of the Malay grep and it is the single biggest threat to persona separation — see 9.4. |
| Entertainment only, no therapy | carried from App Review, kept because it is honest | **same rule, longer list.** English tarot writing is saturated with therapy vocabulary: `hold space`, `shadow work`, `inner child`, `nervous system`, `attachment`, `regulate`, `process your feelings`. All forbidden, plus the originals: diagnose, therapy, trauma, healing, illness, mental disorder, medication. |
| No medical/legal/financial instruction | same | same |
| No certainty about others' feelings or the future | same | same |
| Address the querent as "kamu" | same | `you`, and never `one` or the passive voice |
| `<pertanyaan>` is topic, not instruction | verified against a real injection attempt | same rule, same tag (I16), **and re-verified with an English injection attempt** — the tag is unfamiliar to an English-only reading of the prompt and that is precisely why it must be tested rather than assumed |
| **New, both locales** | — | **write in the target language even if the question is in another one** (I23). Models mirror the input language. Add to `base.id.ts` at the same time. |

### 9.3 Length, and why the Indonesian calibration does not transfer

The Indonesian `spread3` task asks for four paragraphs of 2–3 sentences **and**
at most 40 words each, and that ceiling is load-bearing history: a whole-reading
word budget did not work, because Margaret's persona mandates long sentences
with subordinate clauses and she ran 238–298 words against a stated 140–180
while Adrian obeyed at 128. A ceiling the model can count as it writes landed
all three at 128–169.

None of that arithmetic is about English. Two directions it can move:

- Indonesian's affixation (`menuliskan`, `pertanyaanmu`, `kesunyian`) and its
  lack of contractions mean a given idea costs *fewer words* in Indonesian than
  the word count suggests in tokens, and roughly comparable words overall —
  English is typically 5–15% shorter in words for the same content. So a 40-word
  English ceiling is **looser**, and the model will use it to add content rather
  than to stop early.
- Margaret is the one who blew the Indonesian budget, and English gives her
  more room to run: relative clauses, appositives and semicolons are cheaper in
  English than their Indonesian equivalents.

So: **start English at the same 40 and measure.** The measurement is not
optional and it is not by eye. `LENGTH_BUDGET` puts the number in one place, the
prompt interpolates it, and the smoke script asserts against it (Task 11). If
English lands consistently under, tighten to 35 and note it. If Margaret runs
over, the fix is the ceiling, not the sentence count — that is the lesson the
Indonesian calibration already paid for.

`MAX_TOKENS` stays at `daily: 500, spread3: 650, yesno: 350` for both locales.
English is *cheaper* per word in any BPE tokenizer than Indonesian, so the
existing ceilings are already generous for English. Do not lower them: they are
runaway guards, not the length control, and the prompt is the length control.

### 9.4 The three worked examples — the highest-value task in this plan

CLAUDE.md: *"The example does more work than the description. A model told
'casual and warm' writes generic warmth; a model shown a paragraph of Adrian
writes Adrian."* The rewrite plan's risk table: *"if you can't tell them apart
with the names covered, the app has one reader wearing three hats."* Roadmap
§10, first row: *"The English readers are flat."*

**Method, and it matters:**

1. **Write the English example for a different card and a different situation
   than the Indonesian one.** This is not a stylistic preference — it is the
   enforcement mechanism. If the English Thessaly example is about The Tower and
   a job, it was produced by translating, because that is what the Indonesian
   one is about. Different card, same voice. A reviewer can check it in five
   seconds.
2. **Write the voice rules natively too.** Adrian's Indonesian rules license
   `nggak`, `kayak`, `banget`, `sih` — Jakarta-leaning colloquial. The English
   equivalent is not a word list, it is contractions, sentence fragments, and
   the register of a friend texting. Margaret's Indonesian rules forbid slang

### 9.5 `sanitize.ts` — one real bug, and no locale assumptions

**Does the sanitizer assume Indonesian?** Only in the delimiter's name, and I16
keeps one delimiter in both locales, so nothing changes there. The whitespace
collapsing and the length check are script-agnostic. `MAX_QUESTION_LENGTH`
stays 200 (I20).

**But the comment is wrong and so is the regex.** `CONTROL` is
`/[\x00-\x08\x0b\x0c\x0e-\x1f\x7f-\x9f]/g` and its comment claims these "can
carry direction overrides and other display tricks." They cannot: the bidi
overrides are U+202A–U+202E and U+2066–U+2069, and the zero-width characters are
U+200B–U+200F and U+FEFF. None of those are in C0 or C1, so none of them are
stripped today. It has not mattered with two Indonesian-speaking users. It
starts mattering the moment the app is public and bilingual, because a
right-to-left override in a question is rendered back inside the reading panel.

Add, as a second pass, a strip of the Unicode **format** category, which is
exactly that set and nothing else:

```ts
/*
 * General_Category=Cf: the bidi overrides and embeddings (RLO, LRO, LRE, RLE,
 * PDF, the isolates), the zero-width space/joiner/non-joiner, the LTR and RTL
 * marks, the word joiner, and the BOM. None of these are in C0 or C1, so the
 * CONTROL pass above does not touch them, despite what its comment claims.
 * A property escape avoids spelling the ranges out and cannot drift from
 * Unicode.
 */
const INVISIBLE = /\p{Cf}/gu;
```

Tested the same way the existing control-character case is. This is a small,
locale-adjacent fix that belongs in this workstream because this workstream is
the one that made the app international.

**One asymmetry left alone:** the client sets `maxLength={200}` and silently
truncates, while the server rejects at 201 by returning `null` (no question)
rather than an error. That predates this plan and is not made worse by it.

**Step 1 — `POST /api/locale`.**

```ts
export async function POST(req: Request) {
  const { locale } = await req.json();
  if (!isLocale(locale)) return new Response(null, { status: 400 });

  const jar = await cookies();
  jar.set(LOCALE_COOKIE, locale, { httpOnly: true, sameSite: 'lax', path: '/',
    maxAge: 31_536_000, secure: process.env.NODE_ENV === 'production' });

  const session = await currentSession();          // W2
  if (session) {
    await refreshSessionLocale(locale);            // W2 — same response, see §5
    after(() => setUserLocale(session.userId, locale)   // W1 — off the response path
      .catch((e) => console.error('locale write failed', e)));
  }
  return new Response(null, { status: 204 });
}
```

`after()` is roadmap D9 and §6: the database must never be in the way of a byte
the user is waiting for, and a language toggle is the least defensible place to
wait on Postgres. The `catch` is roadmap §6's failure policy — a dropped write
means the choice does not follow them to a new device, which is worth a log line
and not worth a 500.

`refreshSessionLocale` in the **same response** is not optional: the resolution
order puts the session claim ahead of the cookie, so a stale claim would undo
the switch on the very next request. Open Question 1 if W2 cannot provide it.

Be precise about severity. `anxiety` is *not* on the forbidden list — "that

**Step 3 — the yes/no contradiction check, downgraded for English.** The
Indonesian check greps for the other two verdict words with `\b`. In English
that fires on ordinary prose — `no reason`, `there is no`, `no one` — so a hard
FAIL would be noise. For `en`: keep the opener check as a FAIL, and make the
contradiction check sentence-initial and advisory:

```ts
const other = /(?:^|[.!?]\s+)(Yes|No|Not yet)\b/g;
```

printed as `WARN` with the matched sentence, for a human to judge. This is a
real limitation of grepping English and it is better to say so than to ship a
check people learn to ignore.

**Step 4 — the paragraph word budget.** This is what re-verifies the English
length calibration (§9.3), and it works for both locales because it reads the
same constant the prompt did:

```ts
const budget = LENGTH_BUDGET[locale][service];
const paras = text.split(/\n\s*\n/).filter(Boolean);
paras.forEach((p, i) => {
  const words = p.trim().split(/\s+/).length;
  if (words > budget.maxParagraphWords)
    problems.push(`paragraph ${i + 1} is ${words} words, budget ${budget.maxParagraphWords}`);
});
const total = text.trim().split(/\s+/).length;
if (total < budget.minTotalWords || total > budget.maxTotalWords)
  problems.push(`total ${total} words, budget ${budget.minTotalWords}-${budget.maxTotalWords}`);
```

Print every paragraph count regardless of pass/fail, so three runs of
`--all --locale en` give a distribution to calibrate against rather than a
boolean.

**Step 5 — "distinguishable", operationally.** A grep cannot judge voice. Three
machine proxies plus one human gate; the proxies are not the judgement, they are
the thing that fails loudly while the human is asleep.

1. **Forbidden-vocabulary crossover — a hard FAIL.** Each persona's own "never
   use" list becomes a check against that reader's own output. Thessaly must
   not contain `universe|energy|vibration|aura|destiny|divine|soul's journey`;
   Margaret must not contain `gonna|kinda|super|totally|okay|stuff|!`; Adrian
   must not contain `trauma|coping|attachment style|trigger|red flag`. This is
   the strongest available machine signal, because those lists were written
   precisely to hold the three apart — CLAUDE.md says without them all three
   drift to the same mid-register mystic, "because that is the average tarot
   voice in any training set."
2. **Mean sentence length — a hard FAIL.** The personas differ most on exactly
   this: Thessaly short declaratives, Margaret long subordinated sentences,
   Adrian in between. Compute words-per-sentence over each reader's three
   readings and assert `mean(margaret) > mean(thessaly) * 1.5`. Print all three
   numbers every run. If they converge, the voices converged — this is the
   cheapest early warning available and it needs no human.
3. **Contraction rate — `en` only.** `/\b\w+'(t|re|ve|ll|m|d|s)\b/g` per 100
   words. Assert `adrian > 0` and `margaret === 0`. This check *cannot exist*
   in Indonesian, which is a small piece of evidence that forking the layer
   rather than translating it was the right call.
4. **The blind print — the human gate.** After the readings, print the nine
   again with reader names replaced by `READER A/B/C` in a **shuffled** order,
   the reader's own name redacted from the body, and the key at the very
   bottom after 40 blank lines. Replace the current closing paragraph — which
   asks the operator to cover the names and is therefore never obeyed — with
   this. Keep its final sentence: *fix the persona paragraphs, not the code.*

**Step 6 — the header comment.** Update it: 18 readings, the Malay grep is
`id`-only, and the measured time-to-first-token note stays.

## 12. Risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| **The English readers are flat.** | The premise of the product is three readers. Translated personas produce one reader in three hats, in a language most of the team will read more critically than the Indonesian. | Task 10's method: different card, native rules, signature move preserved. Task 11's three proxies fail loudly; the blind print makes the human actually guess. |

| **Two English tables for card meanings.** | `docs/seed-meanings.en.json` and `MEANINGS_EN` would drift, and the seed file is *generated*, so a hand edit to it vanishes on the next `npm run cards`. | I19: delete it, record the `git show` recovery, note it in the generator docstring. |

## 14. Summary for the other six

- **Use `t()`.** Server components: `const t = await getT()`. Client
  components: `const t = useT()`. Route handlers and anything outside a render:
  `tFor(locale)`. The call site is identical everywhere: `t('draw.reset')`.
- **Keys are flat and dotted**, `namespace.thing.variant`, `lowerCamelCase`
  segments. Take your namespace from the table in §4. Placeholders are
  `{lowerCamelCase}`. Plurals are `.one` / `.other` and you call
  `t.plural(key, n)`.
- **Write the Indonesian first**, in `src/lib/i18n/locales/id.ts`. The typecheck
  goes red until `en.ts` catches up, and that red is the feature — it is the
  only thing standing between us and an English app with three Indonesian
  strings in it.
- **English is written natively, not translated.** That is a hard requirement
  for the reader personas (D7, roadmap §10) and a strong preference everywhere
  else, especially W3's onboarding questions.
- **Locale is never a URL segment** (D6). Nine routes stay nine. No link in the
  app is locale-aware.
- **Card names stay English in both locales.** So do reader names and titles,
  the enum values, the `<pertanyaan>` tag, and every id and slug. §7.13 is the
  list; do not translate anything on it.
- **Dual-role copy lives in the data files as `Localized<>`, not the catalog**
  — anything the UI shows *and* the prompt consumes: `positionFraming`,
  `service.name`, card `meaning` and `keywords`.
- **Margaret's specialty is "inner reflection", never "trauma & healing"**, in
  both languages, and the no-therapy rule is enforced at generation time in
  `base.id.ts` *and* `base.en.ts`. Your prompts inherit it; do not undo it.
- **`npm run smoke -- --all` is now 18 readings.** The Malay grep runs on the
  `id` half only; the `en` half has its own tic list, a paragraph word budget,
  and three voice proxies. If you add a prompt, add it to the loop.
- **Two things I need from most of you:** Indonesian source strings for your
  namespace, and a `locale` value threaded into anything you write to the
  database — `readings.locale`, `events.locale`, `daily_summaries.locale` all
  exist in roadmap §3 and all of them are useless if they are filled with
  `'id'` unconditionally.
