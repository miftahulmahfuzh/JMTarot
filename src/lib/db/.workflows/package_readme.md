# Package: `db` — the data layer

**Location**: `src/lib/db`
**Last Updated**: 2026-08-28
**Documentation Created**: 2026-08-28 (initial creation, on task `P1-DB-A000`)

## Overview

`src/lib/db` is the only part of JMTarot that knows Postgres exists. It owns the
Drizzle schema for all twenty-two tables, the single `postgres.js` connection
(named in exactly one file), AES-256-GCM field encryption for the two
highest-liability columns, the committed migration history, one query module per
read concern, and the integration-test harness that lets every one of those query
modules be exercised inside a transaction that is always rolled back.

Nothing above this package writes SQL. Route handlers, `after()` callbacks,
scripts and Vitest all reach the database through a function in `queries/**` that
takes its handle as its first argument — which is what makes a caller able to
compose two tables atomically, and what makes a test able to hand in a rolled-back
transaction instead of a real connection.

**Key responsibilities:**

- **Schema ownership.** `schema.ts` is the single source of truth for tables,
  columns, indexes and the `New*` / row types every consumer imports. It has one
  owner (W1); other workstreams declare deltas in their plan and have them folded
  in.
- **Connection policy.** `client.ts` is the one place the driver is named, and the
  one place the three Neon knobs (`max: 1`, `prepare: false`, `ssl: 'require'`)
  are decided — keyed off `VERCEL`, not `NODE_ENV`.
- **Query surface.** ~30 modules under `queries/` (14 app-facing, 13 under
  `queries/admin/`), each one read concern, each returning domain shapes rather
  than query builders.
- **Field encryption.** `crypto.ts` encrypts `onboarding_answers.answer_text` and
  `moderation_flags.question` in the application, with a greppable `v1.` prefix so
  "is this column actually encrypted?" is a one-line audit query.
- **Migration history.** Generated by `drizzle-kit`, committed, applied by
  `npm run db:migrate` locally and by `npm run build` on Vercel. `drizzle-kit push`
  is banned.
- **Test infrastructure.** `testing/harness.ts` (`withRollback`, `resetDb`) and
  `testing/globalSetup.ts`, on their own `TEST_DATABASE_URL` client that refuses
  any database whose name does not end in `_test`.

## The contract every file in `queries/` follows

Stated in `queries/profile.ts`'s header, enforced by `queries/contract.test.ts`
(a unit test — it reads the files off disk and needs no database):

1. **Every exported function takes the handle first**: `(db: DbOrTx, ...args)`.
   No module-level `import { db }`. This is what lets a test pass a rolled-back
   transaction and what lets a caller write two tables atomically inside one
   `db.transaction()`.
2. **Import the type, not the value**: `import type { DbOrTx } from '../types'`,
   never from `'../client'`.
3. **No React, no Next, no `server-only`.** Not `next/cache`, not `next/headers`,
   not `react`'s `cache()`. These modules are called from route handlers, from
   `after()`, from `scripts/db-seed.ts` and from Vitest, and three of those four
   have no React runtime. Caching is the caller's decision.
4. **Return domain shapes, not query builders.**
5. **One file per read concern.** A function that fits none of the existing files
   means the concern is new — add a file and say so in the plan, do not widen an
   existing one into a junk drawer.

`client.ts` is the single exception to rule 3's `server-only` clause, and
`contract.test.ts` excludes it **by name** so that a second file acquiring
`server-only` is a test failure rather than a shrug.

## Exported API

### `types.ts` — type-only, no runtime imports

```ts
export type Db     = PostgresJsDatabase<typeof schema>;
export type Tx     = Parameters<Parameters<Db['transaction']>[0]>[0];
export type DbOrTx = Db | Tx;
```

Separate from `client.ts` on purpose: every query module needs the `Db` **type**
and none needs the `db` **value**, so a module with no runtime imports means a
query module physically cannot acquire the singleton by accident — there is
nothing here to import. `Tx` is extracted positionally rather than imported as
`PgTransaction<...>`, whose four type parameters change between drizzle minors.

### `client.ts` — the singleton

```ts
export const db: Db;
```

`import 'server-only'` at the top; the only file in the package that has it.
Serverless detection is `!!process.env.VERCEL` — a Vercel *preview* build is also
`NODE_ENV=production` and also serverless, while a local `npm run build && npm start`
is neither. Cached on `globalThis` outside production, because `next dev`
re-evaluates modules on HMR and would otherwise leak one pool per save.

**Never import this from a script or a test.** `server-only` throws outside a Next
server bundle. Scripts build their own `postgres.js` client; tests use
`testing/harness.ts`.

### `crypto.ts` — field encryption

```ts
export function answerAad(userId: string, questionKey: string): string;
export function moderationFlagAad(userId: string | null | undefined): string;
export function encryptField(plaintext: string, aad: string): string;   // throws
export function decryptField(stored: string | null | undefined, aad: string): string | null;
export function isEncrypted(stored: string | null | undefined): stored is string;
```

Stored format: `v1.<base64url iv>.<base64url ciphertext>.<base64url tag>`, a flat
~60 characters of overhead. Four properties are load-bearing: the `v1.` prefix is
greppable (`... where answer_text not like 'v1.%'` must return 0); base64url has
no `+ / = $`, so a value is safe in a log line, a URL, a JSON body and a `.env`
file; the version prefix is the rotation seam; and the IV travels with the
ciphertext so nothing else in the schema has to know GCM exists.

**The asymmetry is the design.** `encryptField` throws and `decryptField` returns
`null`. Reversing either gives you, in order: a column of plaintext trauma
descriptions, or an onboarding page that 500s for every user the moment a key is
rotated. An undecryptable answer takes the same path as a skipped one.

The key is memoized **against its source string**, not unconditionally, so
rotation is visible without a process restart and tests that replace the env var
cannot pass off a warm cache. There is deliberately no test-only reset export.

### `schema.ts` — twenty-two tables

`users`, `profiles`, `onboardingAnswers`, `lotusAvatars`, `readings`,
`readingCards`, `events`, `dailySummaries`, `moderationFlags`,
`frequencyVerdicts`, `translations`, `shareLinks`, `personas`, `adminAccessLog`,
`llmCalls`, `blogPosts`, `blogPostLocales`, `adminInsights`, `chatThreads`,
`chatMessages`, `chatRuns`, `authHandoffs`.

Ten landed at W1; the rest arrived one workstream at a time. Each table exports
its row type and its `New*` insert type, which is what the query modules and their
callers pass around instead of anonymous object literals.

Two column-type rules that bite: `local_date` and `birth_date` are `string`, not
`Date` (a `Date` renders in the server's zone and is a day out for anyone in
Jakarta between midnight and 07:00), and Drizzle's `$onUpdate()` does **not** fire
inside `onConflictDoUpdate`, so every upsert in `queries/**` sets `updatedAt` by
hand.

### `testing/`

```ts
export const testDb: Db;
export async function withRollback(fn: (tx: Tx) => Promise<void>): Promise<void>;
export async function resetDb(): Promise<void>;
export async function closeTestDb(): Promise<void>;
export async function setup(): Promise<void>;   // globalSetup.ts
```

`withRollback` runs the body inside a transaction that always rolls back — ~100×
faster than truncating twenty tables per test, and it composes for free with the
handle-first rule, because `tx` satisfies exactly the same parameter as `db`. It
**cannot** test code that opens and commits its own top-level transaction, or
anything spanning two connections; `resetDb()` is the escape hatch for those.

`resetDb()`'s `TRUNCATE` list names every table explicitly even though `CASCADE`
would reach several of them, so that a table added to the schema and forgotten
here shows up as leaked state rather than as a silent survivor. **The list is
maintained in the migration's own commit**, not by a later reconciliation.

Both `harness.ts` and `globalSetup.ts` independently refuse a `TEST_DATABASE_URL`
whose database name does not end in `_test`. That guard is the only thing standing
between a mistyped variable and `TRUNCATE` across development data.

## Internal architecture

### Data flow

```
route handler / after() / server component / script / vitest
        │
        │  requireUser() has already answered "who is this"
        ▼
queries/<concern>.ts        ← takes the handle FIRST
        │
        ├── db          (client.ts singleton, server-only, Next runtime)
        ├── tx          (caller's db.transaction, for multi-table atomicity)
        └── testDb / withRollback's tx   (integration suite)
        │
        ▼
drizzle-orm/postgres-js  →  postgres.js  →  Postgres 16
                                             (Docker locally, Neon pooled on Vercel)
```

Entry points are always a `queries/**` function. Exit is always a domain shape —
a row type, a DTO, or a small `{ ... }` the caller can render. Query builders
never leave the package.

Writes on the reading path go through **one `after()` per request**
(`src/lib/analytics/flush.ts`), which takes an **optional** handle as its *last*
argument and reaches the singleton through a **dynamic** `import('@/lib/db/client')`
— a static import would pull `server-only` into a module Vitest has to load.

### Migrations

Generated and committed under `migrations/`, with `meta/_journal.json` and one
snapshot per migration. `0000_baseline` through `0016_v14-readings-soft-delete`.

The rules live in `migrations/README.md` and are not restated here, except the
three that cost the most when broken:

- **`drizzle-kit push` is banned.** It applies a schema diff without writing a
  migration file, silently desynchronizing committed history from every other
  machine. Only `generate` + `migrate`.
- **Never edit a migration that has been applied anywhere.** Not for a typo. Add
  another one.
- **`meta/_journal.json` is the file that will conflict.** Do not hand-merge it —
  delete your own `.sql` and snapshot, take theirs wholesale, re-run
  `npm run db:generate`.

Code and schema shipping on different rails took production down once. Since then
`npm run build` runs `scripts/db-migrate-deploy.ts` **first** and fails the build
rather than skipping; it needs `MIGRATE_DATABASE_URL` (Neon's **direct** string,
never `-pooler`) and skips off-Vercel on the `VERCEL` guard.

## Dependencies

### External

- **`drizzle-orm`** — the schema DSL, the query builder, and `sql` for the
  handful of expressions the builder cannot express. Its `postgres-js` adapter is
  the only driver binding.

## Concurrency

**The package holds no application-level locks and spawns nothing.** Concurrency
control is Postgres': transactions, `on conflict`, and predicates that make a
second concurrent writer a no-op.

Thread-safety notes:

- `db` is a shared pool handle and is safe for concurrent use. On Vercel the pool
  is `max: 1` per isolate; locally `max: 10`.
- Every mutation that must be all-or-nothing wraps itself in
  `db.transaction(...)` and passes `tx` down. `insertReading`, `softDeleteReading`
  and `deleteAccount`'s redaction sequence are the three that matter.
- **Idempotence is expressed as a `where` predicate, not as a lock.** Two
  simultaneous soft deletes both find the live row; `where deleted_at is null` on
  the final update means exactly one reports `deleted: true` and the other's
  statements are no-ops. `claimRun`'s lease and `claimHandoff`'s
  `where claimed_at is null ... returning` are the same shape.
- The one known gap is at the *deploy* level, not the query level: concurrent
  Vercel builds could both apply one migration, because drizzle takes no advisory
  lock.

## Error handling

There are no custom error types except `chat.ts`'s `LeaseLostError` and
`harness.ts`'s internal `Rollback` (thrown to force the rollback and swallowed by
`withRollback` alone).

The rule that binds every consumer:

> **Never log a driver error from any path that runs a query.**

A postgres error quotes the failing statement **and its bound parameters**, and
`readings.question`, `chat_messages.body` and the onboarding answers are among
them. Production logs the reading id, the attempt, SQLSTATE and the error's class;
development prints the whole thing, because there is nobody to leak it to. The
generalisation is that every `catch` touching the database is a potential PII
sink, and the audit question is *"which of my bound parameters came from a
person?"*

Two consequences visible inside this package:

- Query modules keep their projections **minimal** where a caller is going to log
  a failure — `softDeleteReading` selects `local_date` and nothing else,
  precisely so a driver error cannot carry the querent's own words.
- Malformed uuids are checked against `UUID_RE` and return the empty answer,
  rather than being sent to Postgres to raise `22P02` with the id in the bound
  parameters.

`encryptField` is the only function here that throws by design.

## Performance

- **Allocation is light.** These modules build a query and map rows; nothing
  buffers a large intermediate.
- **`reading_cards` carries denormalized `user_id`, `local_date` and now
  `deleted_at` so its two scans need no join.** `cardCounts` and
  `readingsInWindow` are measured at 0.12ms over 45,000 rows on the
  single-table plan, and that measurement is the entire argument for the
  denormalization. An `exists (select 1 from readings ...)` would replace the scan
  with a semi-join and undo it.
- **`postgres.js` returns bigint aggregates as strings.** Every `count()` result
  goes through `Number()` — a string count compares with `>=` and then sorts
  wrong.
- **`sql<T>` is an assertion the driver is not obliged to honour.** Drizzle maps a
  timestamp to a `Date` when it knows the *column*; inside a raw `sql` template
  there is no mapper and postgres.js returns a **string**. `answersUpdatedAt`
  types its aggregate `unknown` and converts by hand for exactly this reason —
  the version that asserted `Date` was wrong with a green typecheck and a green
  unit suite, and only an integration test calling `.getTime()` saw it.
- **Admin reads are bounded**, by `ADMIN_STATEMENT_TIMEOUT_MS` and by row caps
  (`DETAIL_ROW_CAP = 200`, `READINGS_PAGE = 50`, `READINGS_MAX = 200`,
  `USER_LIST_MAX = 200`).

No benchmark files. The instruments are `EXPLAIN` by hand and
`llm_calls.total_ms` for the model-call paths.

## Usage

### From a route handler

```ts
import { db } from '@/lib/db/client';
import { readingWithCards } from '@/lib/db/queries/history';

const detail = await readingWithCards(db, user.id, readingId);
if (!detail) return new Response(null, { status: 404 });
```

### Two tables atomically

```ts
await db.transaction(async (tx) => {
  await upsertProfileFacts(tx, userId, facts);
  await markOnboardingComplete(tx, userId);
});
```

### In an integration test

```ts
await withRollback(async (tx) => {
  const id = await insertReading(tx, reading, cards);
  expect(await readingsForDay(tx, userId, '2026-08-28')).toHaveLength(1);
});
```

Name the file `*.integration.test.ts`, or the `unit` project picks it up and fails
without a database.

### From a script

Build your own `postgres.js` client. **Never** `import { db } from '@/lib/db/client'`
— `server-only` throws outside a Next server bundle, and scripts under `scripts/`
additionally cannot use top-level `await` (no `"type": "module"`, so tsx
transforms to CJS).

### Gotchas

- **`local_date` is a `string`.** It is the *querent's* calendar day, sent by the
  client. An integration test fails if anyone "fixes" the column to `mode: 'date'`.
- **`$onUpdate()` does not fire inside `onConflictDoUpdate`.** Every upsert sets
  `updatedAt` by hand; dropping that line freezes the column at the first insert —
  which is `daily_summaries`' regeneration throttle and `translations`' entire
  staleness mechanism.
- **A skip is `answer_text IS NULL`**, never an encrypted empty string, which
  would be indistinguishable from a real answer in a dump.
- **`users.locale_source` NULL means `'chosen'`.** Read it through
  `effectiveLocaleSource()`, never raw.
- **`users.deleted_at` and `readings.deleted_at` share a name and share nothing
  else.** The first is restorable for `ERASURE_GRACE_DAYS` and is *not* filtered
  by the all-time reads; the second is final and *is* filtered everywhere. Do not
  "make them consistent".
- **`putTranslation` has exactly one caller**, because it is the only place
  verification happens and an unverified row in that table is the whole failure V2
  exists to prevent.
- **A cache read that fails is a cache miss, never an error.** Stop the database
  and open a translated reading: it must fall back to the source prose with
  nothing but a log line.

## Recent changes

### 2026-08-28 — `P1-DB-A000`: soft delete for readings (Phase 1 of 4)

Phase 1 of the `HISTORY_RETRY_AND_SOFT_DELETE_PLAN.md` plan set. The feature is
about **embarrassment, not disk**: a querent can remove a reading they regret, and
every derived artifact that would otherwise keep speaking about it goes with it.

**Schema.** `readings.deleted_at` and `reading_cards.deleted_at`, both
`timestamptz` and nullable, migration `0016_v14-readings-soft-delete.sql`. No
index — the predicate eliminates almost nothing and both tables' existing indexes
already serve the queries. `reading_cards.deleted_at` is **denormalized on
purpose**, for the same reason `user_id` and `local_date` already are: the two
frequency scans read that table with no join to `readings`, and a sub-select to
find the parent's state would give up the 0.12ms single-table plan.

**Writes.** `softDeleteReading(db, userId, readingId)` in `queries/history.ts`, one
transaction, in this order and not alphabetical order:

1. read the live row for its `local_date` (the smallest projection that works, so
   nothing user-typed reaches a driver error's bound parameters);
2. `revokeArtifactLinks` — every live `/s/<slug>`, in every language;
3. `clearDaySummaries` — the stored prose that describes the day;
4. flag the card rows;
5. flag the reading **last**.

The revoke and the clear run *before* the flag so that a failure in a statement
that actually removes something aborts the whole delete, rather than leaving a
reading marked deleted with a live public URL. `src/lib/account/delete.ts` is the
precedent and its argument transfers exactly. `userId` is in every `where`,
including the cards' — a reading id reaches the browser, so a statement keyed on
it alone would be a delete token. A malformed uuid is a no-op, not a driver error.
Returns `SoftDeleteOutcome` for tests and logging; the route puts none of it on
the wire.

**`clearDaySummaries(db, userId, localDate, readingId)`** is new in
`queries/summary.ts`. It exists because `isStale` fires on a *new* source id and
cannot see a *removed* one, so filtering `readingsOnDay` is necessary and not
sufficient — without it the reader keeps recounting a day with the deleted reading
in it, for ever. Keyed on `$1 = any(source_reading_ids)` rather than on the day,
so a summary written before the reading was taken is left alone. A delete, not a
flag: this is a read-through cache and the next visit regenerates it.

**Reads.** Sixteen filters added across five modules, always as
`isNull(...deletedAt)` inside the existing `and(...)`, never as an `exists`:

- `history.ts` — `recentReadings`, `readingsOnLocalDate`, `recallableReadings`
  (the sixth filter, and the sharpest: recall is the one path that would quote a
  deleted reading back inside a later reading's prompt), `readingsForDay`,
  `historyDays` (so deleting a day's last reading takes its chip too),
  `readingWithCards` (whose `null` now collapses four cases into one 404 — and
  which is also what `/api/chat/messages`, `/chat?attach=` and `chat/context.ts`
  go through, so one predicate covers four surfaces).
- `frequency.ts` — `cardCounts`, `readingsInWindow`, on the denormalized column.
  Nothing has to invalidate the cached verdict: `fingerprintOf` moves when a
  reading leaves, so `frequency_verdicts` self-invalidates.
- `allTime.ts` — all four reads. `recentReadingIds` filtering is what moves
  `personaInputHash`, so the persona regenerates on the next visit through the
  ordinary mechanism, with no new code.
- `share.ts` — `ownsShareableReading`, `shareableReadingSource` (kept identical to
  each other) and `publicReadingQuery`, the third enforcement and the one with no
  session behind it.
- `summary.ts` — `readingsOnDay`. This does **not** contradict that function's
  "no filters" header, which is about `failed` and `aborted`: "you drew three
  times today" is true whether or not the third finished, but a deleted reading is
  one the querent asked not to remember.

**A new import edge inside the package.** `queries/history.ts` now imports
`revokeArtifactLinks` from `queries/share.ts` and `clearDaySummaries` from
`queries/summary.ts` — the first time a query module imports two others, and
deliberate: the three statements have to share one transaction.
`src/lib/account/delete.ts` is the precedent in full. Both are safe imports
(neither carries `server-only`, `react` or `next/*`), and `contract.test.ts`'s
transitive walk now follows `history.ts` into both.

**Consumer.** `DELETE /api/history/[id]` returns **204 with no body for all four
outcomes** — deleted, already deleted, not yours, never existed — so the route is
not an existence oracle. `logHistoryFailure`'s `surface` union grew `'delete'`
(and `'retry'`, declared here in Phase 1 rather than by the phase that will use
it, because a union with two owners is how a merge drops one of them).

**Tests.** `queries/history.softDelete.integration.test.ts` and
`src/app/api/history/[id]/route.contract.test.ts`.

## Notes

- **`schema.ts` has one owner.** If you need a column, it goes in your
  workstream plan's `## Schema deltas` section and reconciliation folds it in. Do
  not edit `schema.ts` for a table you did not add — several agents inventing
  `user_id` / `userId` / `uid` is the single most likely way this layer becomes a
  mess.
- **No migration in this project inserts a row.** Migrations are schema; a
  migration that inserts application rows runs in production too. The two dev
  users (`google_sub = 'dev:miftah'` and `'dev:jodith'`) exist precisely because
  they do not exist there, and `npm run db:seed` is what makes them.
- **`npm run test:all` is not a true answer** for this package. Run
  `npm test` (unit, no Docker) and `npm run test:integration` (needs
  `npm run db:up`) separately — the combined run races on the shared
  `serverless-redis-http` and fails a shifting subset of the limiter tests.
- **Deferred, not forgotten:** `readings.deleted_at` has no retention sweep yet —
  the timestamp exists so a future one can find rows old enough to erase for
  real, and that is what a boolean would not have supported.
