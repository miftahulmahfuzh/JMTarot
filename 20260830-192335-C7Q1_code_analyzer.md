## Detailed Requirements Understanding

**Problem/Requirement Statement**

Two independent changes to the tail of a finished reading, which is rendered by two different code paths that happen to look identical on screen.

*R1.* Today the tail offers exactly two controls, both outlined text buttons stacked vertically, and neither of them goes anywhere except deeper into this reading. There is **no way back to the reader picker** and **no account control at all** on either screen — `AccountButton` is mounted on `/`, `/[reader]`, `/account` and `/history`, and deliberately not on `/[reader]/[service]` (a denylist test enforces it) nor on `/history/[id]` (an absence, no test). The querent's only exits are the browser back gesture and, on the draw screen, the `Ulang` button in the fixed footer, which reshuffles rather than leaving.

The request is a horizontal row of 44px circles in the page flow — home, share, account — styled from the same tokens the corner chrome uses, replacing the `BAGIKAN` text button, with `Bahas di grup` promoted to the one emphasised control.

*R2.* Every hairline-separated block under a reading owns its own top spacing and inherits its bottom spacing from the next block's `margin-top` plus the page's flex `gap`. The two are not equal and were never derived from each other, so a block reads as top-heavy: 14–18px above the text, 40px below it.

**Success Criteria**

- On the draw screen after `reading.status === 'done'`, and on `/history/[id]` for a readable reading, the tail reads: disclaimer, hairline, emphasised `BAHAS DI GRUP` + hint, hairline, a centred row of three circles (home, share, account).
- Tapping home lands on `/` (the reader picker for a signed-in querent). Tapping share opens the existing share sheet unchanged. Tapping the lotus opens the existing `AccountMenu`.
- Measured at 320/360/390: the distance from a hairline to the first text below it equals the distance from the last text above a hairline to that hairline, everywhere in the tail, on both screens.
- `npm test`, `npm run typecheck` and `npm run build` all green.

**Key Considerations**

1. **Roadmap §7 trap 4 is live and is the reason the account circle is absent from the draw screen.** `readings.locale` records the language the prose came out in, `router.refresh()` keeps client state, and `Draw.tsx` holds the finished prose in React state with no translation path — so a language flip after a completed reading leaves Indonesian prose under English chrome. Mounting an account control there is only safe with the Language row suppressed, permanently, on that screen. `/history/[id]` has no such problem: it renders through `ReadingView`, whose rule 4 and `refillView`'s `shownProse` already handle a locale mismatch.
2. **The suppression is enforced by the absence of an import**, and `accountSurface.test.ts` reads importers of `@/components/AccountButton` by path. A new intermediary component in `src/components/` would make the draw screen's entry invisible to that test — the exact failure a deny-shaped guard exists to prevent. The guard has to learn the hop.
3. **`account.opened.surface` is a closed four-value union in `events.ts`**, which has one owner per release and a machine-checked ceiling. Two new mount points need two new values.
4. **The "two primaries" rule in `AttachReadingLink.module.css` is what R1c reverses**, and it is written down in that file as a decision to be made *once, in both files*: `Bahas di grup` and `Bagikan` are siblings under one reading and neither may be filled. With `Bagikan` becoming an icon they stop being siblings, which is what licenses the emphasis.
5. **`ShareFooter` renders its own hairline wrapper**, so it cannot be dropped into a row without a variant.
6. **No React renderer exists in this project.** `npm test` is logic-only; every assertion about these components is source-level (`ShareFooter.test.ts` and `chatSurface.test.ts` are the precedents). The visual result is loop 4 (`getBoundingClientRect` at fixed widths) and loop 6 (a real iPhone).

**Assumptions**

- *"the existing akun button there"* means the same control and the same menu, relocated into the row on these two screens — not a second, different account affordance.
- R2's *"the same spacing value accross all texts"* resolves to **18px**, because R2 names the `Bahas di grup` block's top spacing as the reference and that value is 18px. The disclaimer's current 14px therefore moves up to 18px rather than the row moving down to 14px.
- *"homepage (card reader selection)"* is `/`, which renders the reader picker for a signed-in querent and the landing page for a stranger. Both these screens are gated, so it is always the picker.

## Current Dataflow

### Entry Point A: the draw screen, after a completed reading

**Location:** `src/app/[reader]/[service]/Draw.tsx:593` (`<main className={styles.shell}>`)

`.shell` is `display: flex; flex-direction: column; gap: 18px` (`page.module.css:1`). Its children, in order, are the back link, the title, the hint, the question field, `Slots`, `.bleed` (the fan), `ReadingPanel`, and — only when `reading.status === 'done' && finished.current && finished.current.id !== 'unknown'` — a **fragment** holding `AttachReadingLink` and `ShareFooter`. A fragment emits no DOM node, so both are direct flex children and both receive the 18px gap.

**`ReadingPanel`** (`ReadingPanel.module.css`):

- `.panel` — `border-top: 1px solid var(--gold-hairline); padding-top: 20px; gap: 14px`
- `.text` — the prose, `margin: 0`
- `.disclaimer` — `border-top: 1px; padding-top: 14px; margin: 6px 0 0`, rendered for `done` and `error`

**`AttachReadingLink`** (`AttachReadingLink.module.css`):

- `.wrap` — `margin-top: 22px; padding-top: 18px; border-top: 1px; gap: 8px`, column, centred
- `.action` — outlined chip, `min-height: 44px`, `padding: 12px 28px`, `border: 1px solid var(--gold-hairline)`, `background: transparent`, `color: var(--muted)`; declaration-for-declaration equal to `ShareFooter`'s `.action`
- `.hint` — italic body serif, `--fs-hint`, `--label`, `max-width: 30ch`, centred

**`ShareFooter`** (`ShareFooter.tsx:231`):

- `.footer` — `margin-top: 22px; padding-top: 18px; border-top: 1px`, `justify-content: center`
- one `<button className={styles.action}>{t('share.action')}</button>` whose `ref` is `opener`
- the sheet, portalled at `z-index: 1000`, opened by `openSheet()`

### Entry Point B: `/history/[id]`

**Location:** `src/app/history/[id]/HistoryDetail.tsx:504`

Mounts `ReadingView` with `prose={shownProse}` and a `footer` slot holding the same fragment: `AttachReadingLink` (gated on `attachable(view)`) then `ShareFooter` (gated on `view.status === 'ok' && view.body !== null`).

`ReadingView`'s `.view` is `display: flex; flex-direction: column; gap: 18px` — **the same 18px as the draw shell**, which is why the two screens' tails measure identically today.

`ReadingView.module.css`:

- `.prose` — `border-top: 1px; padding-top: 20px; gap: 14px`
- `.disclaimer` — `border-top: 1px; padding-top: 14px; margin: 6px 0 0` (byte-identical to `ReadingPanel`'s)
- `{footer}` is rendered directly after `.disclaimer`, as a sibling flex child

### The measured spacing today

Distances as the querent sees them, on both screens (they agree because both parents gap at 18px):

| Distance | Value | Where it comes from |
|---|---|---|
| hairline → disclaimer text | **14px** | `.disclaimer { padding-top: 14px }` |
| disclaimer text → next hairline | **40px** | parent `gap: 18px` + `.wrap { margin-top: 22px }` |
| hairline → `BAHAS DI GRUP` | **18px** | `.wrap { padding-top: 18px }` |
| hint text → next hairline | **40px** | parent `gap: 18px` + `.footer { margin-top: 22px }` |

Both blocks are top-tight and bottom-loose by 22–26px. **The bottom distance is not owned by the block that appears to have it** — it is the *next* sibling's `margin-top` added to the parent's `gap`, which is why it reads as a single number in the screenshot and is two numbers in the source.

### The corner chrome, which R1 asks the row to look like

`AccountButton.module.css` `.button` — `position: fixed`, `top: calc(10px + env(safe-area-inset-top))`, `right: calc(10px + env(safe-area-inset-right))`, `z-index: 800`, `44x44`, `border-radius: 50%`, `color: var(--gold-pale)`, `background: var(--gold-wash)`, `border: 1px solid var(--gold-hairline)`, `backdrop-filter: blur(6px)`; hover/focus lifts to `--gold-text` / `--gold-wash-strong` / `--gold-border`.

`ChatButton.module.css` `.button` — identical except the geometry comes from `--corner-size` / `--corner-inset` / `--corner-slot-1`. Both hold `.mark { width: 22px; height: 22px }`.

**So "the same theme" is a closed set of eight declarations, all from `tokens.css`, and only `position/top/right/z-index` are corner-specific.**

### State Changes

None. Both requirements are presentation-only: no route, no query, no column, no model call, no analytics event added.

The one **stored** side effect that moves is `account.opened { surface }`, which gains two union members. `sanitizeProps()` and the `events` row shape are untouched.

### Exit Points

- Home icon → a client-side navigation to `/`. On the draw screen this unmounts `Draw`, whose cleanup aborts an in-flight reading — **which is why the row may only render at `status === 'done'`**, the same clause `AttachReadingLink` already sits behind.
- Share icon → `openSheet()`, unchanged: `GET /api/share?entity=reading&entityId=…`, then optionally `POST /api/share`.
- Lotus → `AccountMenu`, portalled, whose items navigate away or sign out.

## Key Data Structures

### `AccountSurface`

**Location:** `src/components/AccountButton.tsx:11`

```ts
export type AccountSurface = 'reader_picker' | 'service_picker' | 'account' | 'history';
```

**Used in:** `AccountButton`'s `surface` prop; `track('account.opened', { surface })`; and it must stay assignable to `events.ts:538`'s `'account.opened': { surface: … }`. The two are separate declarations that are kept in step by the `track()` call typechecking — widen one without the other and the build fails, which is the desired behaviour.

### `ShareFooterProps`

**Location:** `src/components/ShareFooter.tsx:170`

`{ entity, entityId, preview, prose, nickname? }`. `prose` is required on purpose (the sheet's "exactly what they will see" promise). Nothing in it describes how the *trigger* looks — the trigger is hard-coded at line 231–239 inside `<div className={styles.footer}>`.

### `ReadingViewProps.footer`

**Location:** `src/components/ReadingView.tsx:180`

A `ReactNode` rendered after `.disclaimer`. Its header states the rule the row must respect: *"the disclaimer stays the last thing above the CTA in all three mounts. Do not wrap `ReadingView` in a container that appends a footer after it."*
