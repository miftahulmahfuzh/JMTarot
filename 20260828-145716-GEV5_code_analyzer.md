## Detailed Requirements Understanding

### Problem / requirement statement

**Feature 1 — `Coba ulang`.** A reading whose stream died before any token arrived is stored
with `body IS NULL`. `readingsForDay` computes `hasBody` in SQL, `HistoryItemRow` renders
`history.item.unfinished` from it, and `/history/[id]` renders `history.detail.noBody`. There
is no way forward from either screen. The requirement is a control that **regenerates prose for
that same reading, over that same hand**, and stores it.

**Feature 2 — swipe to delete.** The `/history` list row is one large `<Link>`. The requirement
is a horizontal swipe that reveals a trash control, which soft-deletes the reading so it stops
appearing anywhere the querent or anyone else can see it.

### Success criteria

Feature 1:
1. A row with no prose offers a clearly-labelled retry; a row with prose never does.
2. The retry regenerates over the **stored draw** — same card ids, same positions, same
   reversals. It never reshuffles.
3. The reading keeps its `id`. History does not gain a second entry, and every FK pointing at
   it (`reading_cards`, `llm_calls`, `chat_messages.attached_reading_id`,
   `chat_runs.trigger_reading_id`, `translations.entity_id`, `share_links.entity_id`) still
   points at the reading the querent retried.
4. It spends the same budgets a fresh reading spends and cannot be looped for free.
5. A retry that fails again leaves the row exactly as it was — still `hasBody: false`, still
   retryable.

Feature 2:
1. A soft-deleted reading disappears from the day list, the day strip, the detail page, chat
   attachment previews, chat prompt context and W5 recall.
2. Any live `/s/<slug>` for it stops resolving, in the same transaction.
3. The gesture does not break tap-to-open, and the destructive action is reachable without a
   touchscreen.
4. Nothing is hard-deleted, so the row survives for the operator and for `/admin`.

### Key considerations, edge cases, assumptions

**Feature 1 amends VD14, and the amendment is narrow.** `docs/plans/2026-07-27-history.md:111`
states VD14: *"'Just like at the time they did it' is a reconstruction, not a re-run … The
reading already exists in `readings.body`; regenerating it would cost a model call and produce
different prose, so the querent's memory of what they were told and the app's would disagree."*
**That argument is about a reading that HAS prose. It does not reach a reading with
`body IS NULL`** — there is no remembered text for a regeneration to disagree with. The same
plan's open question 7 (line 3045) records the ask almost verbatim: *"A separate,
clearly-labelled action that starts a NEW reading from the same hand is a different feature and
might be a good one — it is the most obvious thing a querent will reach for on this screen. Out
of scope, worth recording."* This work is that feature, restricted to the empty case.
`src/lib/db/queries/history.ts:323` carries the counter-claim in a comment — *"They render with
a 'this reading did not finish' line and no retry (VD14)"* — and that comment has to be edited
rather than left standing.

**`aborted` is a deliberate abandonment and `failed` is not.** `ReadingStatus` is
`'ok' | 'partial' | 'failed' | 'aborted' | 'blocked'`. `tee.ts` records `aborted` when the
querent navigated away. Offering `Coba ulang` on a reading somebody walked away from is a
different proposition from offering it on one the stream killed — but from the row's point of
view both are `body IS NULL`, and the querent cannot tell them apart. **Assumption taken:
retryability is `body IS NULL`, not a status list**, because that is what the screen already
says and a status the UI never shows must not silently change what a button does. `partial`
rows have prose and are therefore never retryable.

**Update in place, not insert.** Assumption taken, and the argument is in the FK list above.
The cost is that `readings` gains an update path it did not have (`insertReading` is the only
writer today) and that `llm_calls` will carry two `op: 'reading'` rows for one `reading_id` —
which matters because `readingCostsFor` folds every `reading_id`-bearing row with **no `op`
predicate**, so a retried reading's cost in `/admin` becomes the sum of both attempts. That is
arguably correct (both attempts were paid for) and is recorded rather than "fixed".

**The gate.** The question was classified once, before the first attempt. Re-running
`gateReading` costs a classifier call and could in principle flip; skipping it regenerates a
stored question with no gate. **Assumption taken: re-run the gate**, because `gateReading` also
PRIMES the reading stream (`src/lib/moderation/gate.ts`) and skipping it would mean rebuilding
the priming by hand — and because a refusal on retry is a correct outcome that the existing
403 path already renders. Cost: one `glm-4.5-flash` call per retry.

**Soft delete has no restore, and the copy must not promise one.** V8's account deletion has a
thirty-day grace period; this does not. Assumption taken: the deletion is immediate and
final from the querent's side, and the copy says so without using the word "permanen" — because
the row is kept.

**`reading_cards` is queried alone.** `cardCounts` and `readingsInWindow` in
`src/lib/db/queries/frequency.ts` select from `readingCards` with **no join to `readings`** —
that single-table scan is the measured 0.12ms plan the file's header defends. Adding an
`exists` sub-select to hide a deleted reading's cards would undo it. Assumption taken:
`deleted_at` is denormalized onto `reading_cards` as well, which is what `user_id` and
`local_date` on that table already are, and for the same reason.

## Current Dataflow

### Entry point A: `POST /api/reading` — how a reading is generated today

**Location:** `src/app/api/reading/route.ts:96`
**Trigger:** `Draw.tsx:273`, a `fetch` from the draw screen.
**Input schema:** `{ reader, service, picks: [{id, reversed}], question? }`. **Card ids and
orientation only** — every word of card text is re-derived server-side from `cards.json`.
**Runtime:** `nodejs`, `maxDuration = 60`.

Ordered stages, all of which a retry has to satisfy:

1. `requireUser()` → `user.id` (`:113`).
2. `validSessionId` + `parseLocalDate` off the two headers (`:116-117`).
3. `locale = await getLocale()` — **the resolved UI locale, not `user.locale`** (`:135`).
4. `readingId = crypto.randomUUID()` (`:151`) — known before anything else so every failure
   event names the attempt, and returned as the `x-reading-id` header.
5. `withAnalytics(ctx, …)` wraps everything below.
6. **Four budgets, in this order** (`:206-253`): `hit(user.id)` and `refusalsExhausted(user.id)`
   concurrently, then `hitGlobal()` alone (it records), then
   `reserveModelCall('interactive')`. A hard-tier refusal is a 429 whose `retry-after` comes
   from the limiter and is **not** the window length.
7. Body parse and validation → `invalid()` 400s that each buffer one event.
8. `getLotusBlock(user.id, locale)` — non-fatal, null is normal (`:296`).
9. `recallChain({...})` — non-fatal, null is normal (`:311`).
10. `buildPrompt({reader, service, picks, question, locale, context})` (`:334`).
11. `track('reading.requested', …)` and, when a chain block was offered,
    `track('memory.chain_offered', …)`.
12. `after(() => scheduleLotusRefresh(user.id))` when the Lotus block is missing or stale.
13. `interrupted = t('reading.error.midStream')` — **resolved before the stream opens**,
    because `start(controller)` has no request context.
14. `cleanQuestion = sanitizeQuestion(question)` — the string the gate moderates *and* the
    string stored in `readings.question`, so the two cannot disagree.
15. `modelStartedAt = performance.now()` — times the call, not the handler.
16. `gateReading({question, locale, start})` (`:395`). Runs the blocklist, **primes** the
    reading by calling `iterator.next()`, and races the classifier against it. Throws
    `ReadingStartError` → 500.
17. Moderation events; `recordModerationFlag` in its own `after()`; on a refusal,
    `after(() => hitRefusal(user.id))` and a **403** with `{ error: 'moderation_blocked' }`,
    **no `readings` row and no `reading_cards`**.
18. `teeReading(gated.stream, { startedAt, failureNotice: interrupted })` → `{ stream, done }`.
19. `defer(async () => { … })` — everything below runs after the response has flushed:
    - `outcome = await Promise.race([done, streamTimeout()])`
    - `splitChoiceMarker(outcome.body, true, cleanQuestion)` → `prose`, then
      `validateChoice(split.choice, cleanQuestion)` → `choice`
    - `track('reading.first_token' | 'reading.completed' | 'reading.aborted' | 'reading.failed')`
    - **`persistReading(row, cards)`** — the row and its cards in one transaction
    - `void recordCall({ op: 'reading', readingId, … })` — the `llm_calls` ledger row, **after**
      `persistReading` and never before it
    - `await extractGist({ readingId, body: prose || null, locale })`
    - `detectCallback(...)` → `memory.chain_used`
    - `await touchLastSeen(user.id)`
    - `await mintOnReadingCompleted({...})` — last, because a lost mint costs one proactive
      message while a lost `persistReading` costs the querent's history
20. Response: `text/plain; charset=utf-8`, `cache-control: no-store`,
    `x-accel-buffering: no`, `x-reading-id: <uuid>`.

**The stage that does not exist for a retry: there is no update path.** `persistReading` calls
`insertReading`, which is `insert … returning` inside a transaction and swallows SQLSTATE
`23505` as "already written by a lost-ack attempt". Re-running it against an existing
`readings.id` would hit that catch and **silently write nothing** — the retry would appear to
succeed and change no row.

### `reading_cards` is read WITHOUT joining `readings`

`src/lib/db/queries/frequency.ts:79` (`cardCounts`) and `:118` (`readingsInWindow`) select from
`readingCards` alone, filtered on the denormalized `readingCards.userId` and
`readingCards.localDate`. The file's header defends that as a measured single-table plan
(0.12ms over 45,000 card rows). **A deleted reading's cards therefore still feed the frequency
verdict** unless `deleted_at` is denormalized onto `reading_cards` too.

### The share path

- `ownsShareableReading` (`share.ts:424`) and `shareableReadingSource` (`:469`) both require
  `status = 'ok'`.
- `publicReadingQuery` (`:523`) requires `status = 'ok'` **and** `body is not null`, and builds
  its projection conditionally — `question` and `choice` ride the same ternary so that
  excluding the question cannot leak a slice of it through `choice`.
- `revokeArtifactLinks(db, userId, entity, entityId)` (`:285`) is what the app calls to stop
  sharing a reading: **per-artifact, every locale**. `revokeShareLink` is the primitive.
- `revokeAllForUser` (`:351`) is V8's; its header says it has no other caller.
- `readings.shared_at` is denormalized from `share_links` for the list badge and **stays
  non-null after a revoke** — "was this ever public" is a different question from "is it now".

**Feature 1 will change:** `readings.body`, `.status`, `.gist`, `.choice`, `.verdict`,
`.model`, `.prompt_version`, `.latency_ms`, `.token_input`, `.token_output` on an existing row;

It must **not** touch `reading_cards`, `readings.id`, `.user_id`, `.reader_id`, `.service_id`,

## Key Data Structures

### `ReadingStatus`
**Location:** `src/data/types.ts:135` — `'ok' | 'partial' | 'failed' | 'aborted' | 'blocked'`.

### `HistoryItem`
**Location:** `src/lib/history/types.ts:~50`.
Declared **here and not in the query module** because `clientBoundary.test.ts`'s import regex
`(?:from|import)\s+['"]([^'"]+)['"]` does not know the `type` keyword, so even an erased
`import type { … } from '@/lib/db/…'` fails the fence in a `'use client'` file.
Carries **no `body` and no `gist`** (H10) — `hasBody` is the boolean computed in SQL, with
`Boolean(...)` on the way out because `sql<boolean>` is an assertion the driver is not obliged
to honour.

### `ReadingDetail`
Same file. Adds `body`. Consumed by `ReadingView` via `HistoryDetail`.

### `ReadingOutcome`
**Location:** `src/lib/analytics/tee.ts`. `{ body, status, truncated, firstTokenMs, totalMs,
chars, usage, errorKind }`. **Snapshotted before its `await` on `usage`** — reading mutable
state after that await is the bug that recorded every abandoned reading as failing for an
unknown reason.

### `readings` (table)
**Location:** `src/lib/db/schema.ts`. Indexes: `readings_user_created_idx (user_id, created_at
desc)` and `readings_user_local_date_idx (user_id, local_date)`. **No `deleted_at`** — the
column at `schema.ts:138` belongs to `users`.
